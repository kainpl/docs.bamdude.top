# Сповіщення

Дванадцять каналів доставки, один редактор, одна конфігурація маршрутизації. Підпиши кожен провайдер на потрібні події, постав тихі години й щоденний digest на провайдер, кастомізуй шаблони на мову. І тринадцятий адресат, який нікуди не йде з ферми: [центр сповіщень](#центр-сповіщень) за дзвоником у sidebar-і — він наповнюється для кожного, хто заходить, незалежно від того, чи налаштований бодай один провайдер.

## :material-bell-ring: Підтримувані провайдери

| Провайдер | Складність | Можливості |
|-----------|:----------:|------------|
| **Telegram** | Середньо | Через бота BamDude з actionable inline-кнопками (clear plate, mark maintenance done, pause/stop). Кожен Telegram-провайдер розсилає лише у свої авторизовані чати, підписані на подію. |
| **Discord** | Легко | URL webhook каналу, форматування embed, прикріплення картинок. |
| **Email (SMTP)** | Середньо | STARTTLS / SSL / plain. Per-provider `to_email` — різні юзери бачать різні тіла. |
| **Pushover** | Легко | Рівні пріоритету, прикріплення картинок до 2.5 МБ. |
| **ntfy** | Легко | Topic-based, опційний bearer-токен, прикріплення картинок. |
| **Bark** | Легко | Тільки iOS, без акаунта. Рівні переривання — **Critical** доставляє крізь Silent mode і Focus. Публічний релей або власний `bark-server`. |
| **Gotify** | Легко | Власний сервер Gotify — токен застосунку в заголовку, пріоритет на подію, фото посиланням. |
| **Notify!** | Легко | Застосунок для iOS (також Mac, браузер, групи) — ID пристрою й токен; живі дії й віджети замкненого екрана на iOS; фото посиланням. |
| **CallMeBot** | Легко | Bridge до WhatsApp / Signal — телефон + API-ключ, URL-encoded повідомлення. |
| **Signal CLI API** | Середньо | Власний [signal-cli-rest-api](https://github.com/bbernhard/signal-cli-rest-api) — номери отримувачів або одна група, прикріплення картинок. |
| **Home Assistant** | Легко | `persistent_notification.create` або будь-який `notify.*` сервіс. Глобальний URL/token Home Assistant з Settings (або `HA_URL` / `HA_TOKEN` env). |
| **Webhook** | Гнучко | Generic JSON або Slack-format POST, кастомні імена полів, base64 картинка, опційний bearer. |

## :material-plus-circle: Додавання провайдера

1. Перейдіть до **Settings** > **Notifications**
2. Натисніть **Add Provider**
3. Виберіть тип провайдера та введіть конфігурацію
4. Натисніть **Send Test** для перевірки (усі типи провайдерів, крім Telegram)
5. Налаштуйте тригери подій
6. Натисніть **Add**

Для Telegram спершу збережіть бота, додайте й увімкніть чат цього бота, а тоді скористайтеся **Send Test** на картці збереженого провайдера.

---

Кожен провайдер підписується на події окремо, і форма пропонує їх усі, згрупованими так само, як у центрі сповіщень: друк, принтери, філамент, AMS, черга, склад, сенсори. Що ти бачиш увімкненим під час додавання — з тим провайдер і збережеться.

## :material-cog: Налаштування на провайдер

### ntfy

Topic-based, безкоштовно, без облікового запису. Найпростіший канал, щоб підняти.

| Поле | Значення |
|---|---|
| **Server** | `https://ntfy.sh` (default) або URL власної self-hosted інстанції |
| **Topic** | Унікальний рядок — будь-хто, хто його знає, може писати, тож роби невідгадуваним |
| **Bearer token** | Опційно; потрібно для self-hosted topic-ів за ACL |

Підпишись на телефоні через [ntfy Android](https://play.google.com/store/apps/details?id=io.heckel.ntfy) чи [iOS](https://apps.apple.com/app/ntfy/id1625396347). ntfy підтримує **5 рівнів priority**, які BamDude мапить на подію:

| Priority | ntfy value | Типове використання |
|---|---|---|
| **Min** | 1 | Diagnostics-style ping-и — без звуку, без бейджа |
| **Low** | 2 | Інформаційне, не-термінове (напр. "first layer complete") |
| **Default** | 3 | Стандартне сповіщення |
| **High** | 4 | Audible / urgent (напр. "filament low") |
| **Urgent** | 5 | Будить пристрій, ігнорує Do-Not-Disturb (напр. "print failed") |

### WhatsApp / Signal (CallMeBot)

Безкоштовний міст до WhatsApp / Signal — без власної бот-інфраструктури.

1. Додай CallMeBot у контакти: **+34 644 51 95 23**
2. Надішли `I allow callmebot to send me messages` через WhatsApp
3. CallMeBot відповість твоїм **API-ключем**

| Поле | Значення |
|---|---|
| **Phone number** | Твій номер у форматі E.164 (напр. `+1234567890`) |
| **API key** | Ключ, який повернув CallMeBot |

### Discord

URL webhook каналу — найпростіший спосіб закинути rich embed-повідомлення з мініатюрами в Discord-сервер.

1. У Discord відкрий settings цільового каналу → **Integrations** → **Webhooks**
2. Натисни **New Webhook**, кастомізуй ім'я/аватар, **Copy Webhook URL**
3. Встав URL у форму провайдера BamDude

BamDude постить як embed-и зі snapshot-картинкою inline, коли вона є.

### Pushover

Per-user push-сервіс з нативними iOS/Android-додатками і on-device priority-ескалацією.

1. Створи акаунт на [pushover.net](https://pushover.net/) і встанови додаток
2. Створи **Application** у дашборді

| Поле | Значення |
|---|---|
| **User key** | Зі сторінки твого акаунту Pushover |
| **API token** | З Application, який ти щойно створив |

У Pushover один **Priority** на провайдера (`-2…+2`, `0` = звичайний) — для всього, що цей провайдер надсилає. Пріоритет на подію є в ntfy і Gotify (див. нижче).

!!! info "Priority 2 (Emergency) вимагає двох додаткових полів"
    Pushover **обов'язково** вимагає інтервал повтору й термін дії для Emergency-сповіщень: вони повторюються, доки їх не підтвердять, тож сервіс відхиляє будь-яке повідомлення з priority 2, де не вказано як часто і як довго. Виставте **Priority** у `2` — і з'являться два поля:

    | Поле | Значення | За замовчуванням |
    |---|---|---|
    | **Повтор екстреного сигналу (с)** | Як часто Pushover повторює | 60 с (мін. 30 с) |
    | **Термін дії екстреного сигналу (с)** | Коли припинити | 3600 с (макс. 10800 с) |

    Надсилаються лише при priority 2 — на решті рівнів Pushover їх ігнорує.

### Bark (iOS)

[Bark](https://bark.day.app/) — безкоштовний iOS-застосунок для push, узагалі без акаунта: встанови, скопіюй device key, який він показує, встав сюди. Більше нічого не обов'язково.

| Поле | Значення |
|---|---|
| **Device Key** | Ключ, який Bark показує на першому екрані — **обов'язковий** |
| **Server** | `https://api.day.app` (типово) або власний `bark-server` |
| **Group** | Опційно — складе сповіщення BamDude в окрему групу в застосунку |
| **Sound** | Опційно — одна зі звукових назв зі списку Bark |
| **Interruption Level** | `Default` / `Active` / `Time Sensitive` / `Critical` |

!!! tip "Critical — саме те, заради чого Bark поруч із ntfy і Pushover"
    | Рівень | Що робить iOS |
    |---|---|
    | **Critical** | Доставляє **крізь Silent mode і крізь Focus** — друк, що став о 03:00, таки достукається |
    | **Time Sensitive** | Пробиває заплановані зведення, не заходячи так далеко |
    | **Active** | Звичайне сповіщення |
    | **Passive** | Приходить без звуку — записане, але не оголошене |

    Заведи *print failed* і *filament runout* на Critical-провайдер Bark, а решту лиши на Default-провайдері, замість будити себе кожною подією.

Самохостний `bark-server` підпадає під ті самі правила адрес, що й самохостний ntfy: у власній мережі — можна, усе, що не є справжнім HTTP-сервісом, — відхиляється. Якщо він за Cloudflare-челенджем, BamDude так і скаже, замість вивалити сторінку челенджа.

!!! info "«OK», який не OK"
    `bark-server` подекуди повідомляє про помилку **всередині** тіла з HTTP 200. BamDude читає тіло, а не довіряє статусу, — тож хибний device key у **Send Test** буде помилкою, а не «надіслано», яке нікуди не дійшло.

### Gotify

[Gotify](https://gotify.net/) — push-сервер, який ти тримаєш у себе; повідомлення показує його застосунок для Android. Створи застосунок у веб-інтерфейсі Gotify і скопіюй його токен.

| Поле | Значення |
|---|---|
| **Server URL** | Твій сервер Gotify, напр. `http://192.168.1.50:8080` — **обов'язкове**. Вставлений повний endpoint `/message` із документації Gotify не ламає нічого — BamDude зрізає його до бази. |
| **App Token** | Токен застосунку Gotify, від імені якого пише BamDude, — **обов'язковий**. Він їде в заголовку `X-Gotify-Key`, ніколи в URL. |

Пріоритети Gotify — від 0 до 10. Рівень на подію обирається в розділі **Пріоритет події (Gotify)** (див. [Пріоритет на подію](#per-event-priority) нижче): «Мін.», «Низький», «За замовч.», «Високий» і «Терміново» йдуть до Gotify як `0`, `2`, `5`, `8` і `10`. Подія, лишена на «За замовч.», іде з `5`. У застосунку Gotify для Android рівні від «За замовч.» і вище відтворюють звук, а «Високий» і «Терміново» спливають.

З налаштуванням **External URL** кадр із камери приходить у застосунок для Android великою картинкою (див. [Фото у сповіщеннях](#фото-у-сповіщеннях)). Самохостний Gotify підпадає під ті самі правила адрес, що й самохостний ntfy: у власній мережі — можна, усе, що не є справжнім HTTP-сервісом, — відхиляється.

### Notify! (iOS)

[Notify!](https://getnotifyapp.com/) — push-застосунок для iOS, є також для Mac, у браузері й для груп; надіслане BamDude доставляє його власний сервер. Скопіюй ID пристрою (або групи) і токен із застосунку.

| Поле | Значення |
|---|---|
| **ID пристрою або групи** | 8–32 латинські літери й цифри — **обов'язкове**. ID, що починаються з `GRP` (група), `WB` (браузер) чи `MC` (Mac), отримують лише push-сповіщення. |
| **Токен Notify!** | Токен, який застосунок показує поряд з ID, — **обов'язковий**. Зберігається, як секрет будь-якого провайдера, і прив'язаний до цього ID. |
| **URL значка** | Необов'язково, HTTPS. |
| **Група сповіщень** | Необов'язково. Порожнє поле групує push за принтером; власне значення збирає їх в одну групу. |
| **Термінові сповіщення про проблеми** | Невдалі й зупинені друки, помилки принтера й виявлення браку ШІ надходять як Time Sensitive; решта push — звичайні. |

**Живі дії (Live Activities, iOS).** З увімкненим перемикачем кожен друк отримує плитку на замкненому екрані й у Dynamic Island з відліком до кінця. Збій, пауза, кінець філаменту чи втрата зв'язку замінюють відлік на проблему. Решту задає **Вигляд живої дії**: приховати назву файлу, показувати етап друку, вигляд індикатора прогресу (смуга, сегменти чи без нього), до шести показників (прогрес, ETA, шар, сопло, стіл, термокамера) замість рядка з назвою файлу, кнопку панелі (HTTPS), символ і колір. Плитка йде за кожним друком сама: перемикачі подій керують лише push, тихі години не дають почати нову плитку, а наявні оновлюються й завершуються, щоденне зведення їх не затримує. Закрита плитка для цього друку більше не з'являється, а плитки переживають перезапуск BamDude. Notify! дозволяє п'ять плиток на пристрій і тримає плитку вісім годин; друк, що ще йде, отримує нову. Тексти плитки — мовою інтерфейсу.

**Віджети замкненого екрана (iOS).** З увімкненим перемикачем кожен активний неархівний принтер, який охоплює провайдер, отримує віджет зі станом і прогресом, без живого відліку. Додай його в налаштуваннях замкненого екрана iOS і вибери принтер. iOS оновлює віджети за власним розкладом, приблизно раз на 15 хвилин. Notify! дозволяє десять віджетів на пристрій, тож *Усі принтери* створюють щонайбільше десять.

Кадр із камери йде посиланням, для якого потрібна HTTPS-адреса **External URL**; одержувачі в браузері й групи отримують лише текст. **Send Test** надсилає push; жива дія починається лише разом із друком. Якщо ти запускав контейнер-компаньйон notify-bambuddy, зупини його, перш ніж вмикати тут живі дії, інакше кожен друк отримає дві плитки.

### SMTP / Gmail

Звичайний SMTP — працює з будь-яким провайдером, що дає username + password auth.

| Поле | Приклад |
|---|---|
| **SMTP host** | `smtp.gmail.com` |
| **Port** | `587` (STARTTLS) або `465` (SSL) |
| **Security** | `STARTTLS` / `SSL` / `plain` |
| **Username** | Повна email-адреса |
| **Password** | App password (не пароль акаунту — Gmail відхилить останній) |
| **From address** | Адреса відправника, яку бачать отримувачі |
| **To address** | Per-provider; дозволяє різним членам команди отримувати різні тіла |

Для Gmail: увімкни 2FA, потім згенеруй [App Password](https://myaccount.google.com/apppasswords) і використай його тут.

### Home Assistant

Zero-config, коли HA вже підключений у **Settings** → **Network** → **Home Assistant** (або через `HA_URL` / `HA_TOKEN` env vars). Якщо лишити поля порожніми, події стають викликами `persistent_notification.create` в дашборді HA.

| Поле | Значення |
|---|---|
| **Service** | Опційно — будь-який сервіс HA, напр. `notify.mobile_app_myphone`. Приймається як `notify.x`, `notify/x` або `api/services/notify/x`. Порожнє = `persistent_notification.create` |
| **Data (JSON)** | Опційно — JSON-**об'єкт**, який іде у вкладене `data` HA, тобто саме туди, куди його кладе автоматизація |

Поле **Data** — це те, від чого залежить поведінка Android-push. Опції mobile-app інтеграції HA живуть там, а не в заголовку й тексті:

```json
{ "priority": "high", "ttl": 0, "channel": "BamDude" }
```

`priority: high` + `ttl: 0` — саме те, від чого сповіщення приходить *негайно*, а не коли телефон наступного разу прокинеться; `channel` дає алертам принтерів власний звук, замість ховати їх серед усього іншого, що надсилає HA.

!!! info "Чому JSON, а не рядки `key=value`"
    Щоб `ttl: 0` лишався числом, якого чекає HA, і щоб вкладені опції взагалі були можливі. Поле перевіряється при збереженні **і** ще раз при надсиланні — некоректне відхиляється перед тобою, а не перетворюється на сповіщення, яке тихо ніколи не приходить.

    Лиши порожнім — і нічого не зміниться: воно надсилається, лише коли заповнене, бо `persistent_notification.create` відхиляє зайві ключі.

!!! tip "Форвард HA-сповіщень в інші канали"
    Використовуй HA-автоматизації, щоб дзеркалити persistent-сповіщення на HA Companion app, Telegram, ntfy тощо — отримаєш єдиний audit log в HA плюс звичний мобільний push.

### Signal CLI API

Повідомлення в Signal через власну інстанцію [signal-cli-rest-api](https://github.com/bbernhard/signal-cli-rest-api). Провайдер названо за тим, з чим він говорить: офіційного API в Signal немає, і BamDude не вдає, що це воно. Спершу зареєструй номер у signal-cli (README того проєкту веде за руку); далі BamDude шле з цього номера.

| Поле | Значення |
|---|---|
| **Signal API URL** | Базовий URL твого signal-cli-rest-api, напр. `http://192.168.1.50:8080`. Вставлений повний endpoint `/v2/send` із його документації не ламає нічого — BamDude зрізає його до бази. |
| **Sender Number** | Номер, зареєстрований у signal-cli, у форматі E.164 (`+380501234567`) |
| **Recipient Type** | **Phone Numbers** — один або кілька отримувачів, рядок за рядком, — або **Group ID** — одна група Signal. signal-cli-rest-api не вміє змішати обидва в одному запиті, тож провайдер — або те, або те; хочеш обидва — додай другий провайдер. |
| **Group ID** | ID групи, як його показує signal-cli; голий id отримає префікс `group.` сам |
| **Authorization** | Опційно — значення заголовка `Authorization`, якщо API стоїть за reverse proxy з автентифікацією (`Bearer …` або просто токен) |

Фото завершеного друку прикріплюється до повідомлення. URL підпадає під ті самі правила адрес, що й самохостний ntfy чи `bark-server`: у власній мережі — можна, усе, що не є справжнім HTTP-сервісом, — відхиляється.

BamDude у Docker, а signal-cli-rest-api ще немає? Штатний `docker-compose.signal.yml` піднімає його поруч із BamDude, і `docker-install.sh` це пропонує — див. [Docker → Сайдкар для сповіщень Signal](../getting-started/docker.md#signal-notifications-sidecar).

### Generic Webhook

Для всього іншого — n8n, Node-RED, кастомні HTTP-ендпоінти, Slack-format інтеграції.

| Поле | Значення |
|---|---|
| **URL** | Твій ендпоінт (HTTPS рекомендовано) |
| **Headers** | Опційно — для `Authorization: Bearer …` тощо |
| **Format** | `generic` (структурований BamDude JSON) або `slack` (тільки `{"text": "..."}`) |

Дивись **Webhook Payload Schema** нижче для форми структурованого JSON.

## :material-code-json: Webhook Payload Schema

Generic-format webhooks шлють стандартизований JSON-конверт: `title`, `message`, `timestamp`, `source`, `event` (рядок типу події), плюс усі event-specific поля піднімаються на top-level ключі, тож automation-tools можуть branch-итися на `event` без парсингу message-тексту.

**`print_complete`:**

```json
{
  "title": "Print Complete",
  "message": "Workshop X1C: benchy.3mf completed in 2h 15m",
  "timestamp": "2026-04-02T14:30:00.123456",
  "source": "BamDude",
  "event": "print_complete",
  "printer": "Workshop X1C",
  "filename": "benchy.3mf",
  "duration": "2h 15m",
  "filament_grams": "15.2",
  "filament_details": "AMS-A T1 PLA: 15.2g"
}
```

**`print_failed`** (і `print_stopped`) несуть додаткові поля `progress` + `reason`:

```json
{
  "title": "Print Failed",
  "message": "Workshop X1C: benchy.3mf failed at 50%",
  "timestamp": "2026-04-02T15:15:00.123456",
  "source": "BamDude",
  "event": "print_failed",
  "printer": "Workshop X1C",
  "filename": "benchy.3mf",
  "duration": "0h 45m",
  "filament_grams": "7.6",
  "filament_details": "PLA: 7.6g",
  "progress": "50",
  "reason": "Filament runout"
}
```

**`printer_offline`** — мінімальний payload, тільки те, що релевантне:

```json
{
  "title": "Printer Offline",
  "message": "Workshop X1C is offline",
  "timestamp": "2026-04-02T14:30:00.123456",
  "source": "BamDude",
  "event": "printer_offline",
  "printer": "Workshop X1C"
}
```

**`first_layer_complete`** — включає base64-encoded JPEG-snapshot у полі `image`:

```json
{
  "title": "First Layer Complete",
  "message": "Workshop X1C: benchy.3mf — Layer 1/200 done",
  "timestamp": "2026-04-02T14:30:00.123456",
  "source": "BamDude",
  "event": "first_layer_complete",
  "printer": "Workshop X1C",
  "filename": "benchy.3mf",
  "total_layers": "200",
  "image": "/9j/4AAQSkZJRg..."
}
```

!!! tip "Декодування картинки"
    Поле `image` — стандартний base64-encoded JPEG. Home Assistant: передай у `notify.mobile_app_*` як `image` data через template. Node-RED: `Buffer.from(msg.payload.image, 'base64')`. Поле присутнє лише, коли snapshot реально був захоплений — не всі події його містять.

!!! info "Slack / Mattermost format compatibility"
    З **format = slack** шлеться тільки `{"text": "..."}` — структуровані поля події відкидаються. Подія з картинкою додає її як посилання (див. [Фото у сповіщеннях](#фото-у-сповіщеннях)). Юзай generic-формат для будь-якої automation, що читає структуровані дані; slack — лише для людино-читабельних channel-постів.

## :material-tune: Тригери подій

Кожен провайдер підписується незалежно. Вимкнення події на одному провайдері не зупиняє її на інших.

**Друк:**

| Подія | Спрацьовує коли |
|-------|------------------|
| `print_start` | Друк запустився на принтері |
| `first_layer_complete` | Завершився перший шар (швидко ловить first-layer фейли) |
| `pause_coming_up` | **Наближається пауза** — попередження незадовго до паузи, доданої у слайсері. Типово вимкнено; див. [нижче](#pause-coming-up). |
| `print_progress` | На 25% / 50% / 75% прогресу, рахуючи від першого шару — поки принтер ще гріється чи готується, нічого не надсилається, хоч який відсоток він показує, — і кожен друк починає відлік заново. Поріг **мінімальної тривалості** глушить їх для друків, коротших за N хвилин — і значення належить кожному отримувачу: кожен чат Telegram має власне (біля чекбокса «Проміжний прогрес» у налаштуваннях чату), кожен інший провайдер — своє (на його картці, біля того ж тогла). Порожньо або `0` = слати завжди; спільного глобального значення немає. Тривалість оцінюється із власного remaining-time принтера на кожному milestone, а невідома оцінка шле, а не вгадує. |
| `print_paused` | Принтер перейшов RUNNING→PAUSE — у тілі нормалізована `{reason}` (двері відкриті / філамент скінчився / presence-check / G-code pause / AI defect / об'єкти на платі / paused by user / HMS-other) плюс `{hms_code}` для forensics. За замовчуванням **ON** для нових провайдерів + входить у дефолтний event-набір Telegram-чату. |
| `print_resumed` | Принтер перейшов PAUSE→RUNNING — у тілі `{paused_for}` (mm:ss) обчислений по delta між edge'ами. За замовчуванням **ON** для нових провайдерів; opt-in для Telegram-чатів. |

Стан паузи також візуалізується на сторінці Принтерів у реальному часі — на картці paused-принтера поряд зі статусом з'являється маленький `<PauseChip>` із класифікованою причиною і живим mm:ss-лічильником, плюс жовта попереджувальна піпка в кутку. Чіп зникає у мить resume; resume-нотифікація несе те саме значення `{paused_for}`, що і chip відраховував.

| `print_complete` | Друк завершився успішно |
| `print_failed` | HMS-помилка / hardware-фейл зупинили друк |
| `print_stopped` | Людина зупинила друк — з картки принтера, з черги, з Telegram-бота, через webhook чи кнопкою **Зупинити друк** у діалозі HMS |
| `print_outcome_unchecked` | **Результат не перевірено** — нагадування, що результат завершеного друку ніхто не перевірив. Типово вимкнено; див. [нижче](#result-not-checked). |
| `bed_cooled` | Стіл охолов до порогу (сигнал готовності зняти деталь) |

**AMS / філамент:**

| Подія | Спрацьовує коли |
|-------|------------------|
| `print_missing_spool_assignment` | Друк стартував без повного мапінгу spool→AMS |
| `filament_low` | Залишок котушки нижче `low_stock_threshold` (або власного порога котушки). Котушка з інвентарю перевіряється, коли лягає витрата друку, одразу, щойно її ставлять у слот уже нижче порога (призначають вручну, розпізнають за RFID-тегом чи автоматично завантажують зі складу), і коли її вагу, вагу за етикеткою або власний поріг змінюють вручну, поки вона стоїть у слоті, — раз на пробіг і лише для котушки в слоті; слот, прив'язаний до Spoolman, перевіряється на кожній зміні AMS, раз на котушку в слоті. Слот без прив'язки до інвентаря ніколи не оцінюється за власним лічильником принтера — котушка без RFID-тега показує 0 %, а це не відповідь, — тож неприв'язаний слот мовчить. |
| `ams_humidity_high` / `ams_temperature_high` | AMS перевищив свій поріг |
| `sensor_above_max` / `sensor_below_min` | Показ [датчика](sensors.md) вийшов за задані для нього межі |
| `sensor_back_in_range` | …і повернувся |
| `sensor_silent` / `sensor_speaking_again` | Датчик перестав звітувати — і почав знову |

**Принтер:**

| Подія | Спрацьовує коли |
|-------|------------------|
| `printer_offline` | MQTT-розрив |
| `printer_error` | З'явився збій HMS рівня «Критично» чи «Помилка» (BamDude додає переклад людською). Про кожен збій повідомляється один раз на появу — див. [Сповіщення HMS](monitoring.uk.md#сповіщення-hms). Через цю подію приходить і [сповіщення про потужність](smart-plugs.uk.md#сповіщення-про-потужність) розумної розетки. |
| `ai_failure_detection` | AI-детекція збою (Obico чи OctoEverywhere) позначила ймовірний провал друку — **opt-in, вимкнено за замовчуванням**. Виділено з `printer_error`, тож можна отримувати AI-алерти без кожного HMS-коду. Має власний шаблон, власний per-provider тоглер і власний per-chat Telegram-пункт; тіло несе принтер, назву роботи, постачальника, оцінку впевненості Obico або якість друку OctoEverywhere (інше — N/A) та дію, яку виконав BamDude (notify / pause / pause + power off), а сповіщення — кадр, який позначив детектор. |
| `plate_not_empty` | Bed-occupancy gate зловив старт наступного друку (auto-pause). Несе кадр, за яким перевірка ухвалила рішення. |
| `maintenance_due` | Інтервал обслуговування досягнуто |

**Черга:**

| Подія | Спрацьовує коли |
|-------|------------------|
| `queue_job_added` / `queue_job_started` / `queue_job_skipped` / `queue_job_failed` | Події черги. Сповіщення «Завдання додано» надходить після успішної дії оператора, одне на групу копій в одній дії. Автоматичне призначення чи повернення наявного завдання AutoQueue повторного сповіщення не надсилає. |
| `queue_job_waiting` | Нові змістовні перешкоди авточерги, зведені в одну подію за прохід. Звичайна зайнятість принтерів — без алертів; див. [сповіщення AutoQueue](auto-queue.md). Не надсилається провайдеру чи Telegram-чату, [обмеженому окремими принтерами](#per-printer-фільтрація). |
| `queue_completed` | Спорожніли черги **всієї інсталяції** — спрацьовує лише раз, коли кожен принтер idle і нічого не лишилось у черзі. |
| `printer_queue_completed` | Спорожніла **власна черга окремого принтера** — спрацьовує у мить, коли цей принтер завершив свою останню задачу, незалежно від того, що роблять інші принтери. |

!!! note "Глобальне vs. per-printer завершення черги"
    На setup-і з одним принтером ці дві події еквівалентні. На **багатопринтерній фермі** вони різняться: `queue_completed` чекає, поки idle стане *кожен* принтер, тож довга задача на одному принтері придушує подію для всіх інших. `printer_queue_completed` спрацьовує per-printer у мить, коли власна черга принтера спорожніла — обери цю, якщо хочеш ping "ця машина вільна, став наступну плату" на кожен принтер. `printer_queue_completed` **ON** за замовчуванням для нових провайдерів; `queue_completed` — off за замовчуванням.

**Інвентар:**

| Подія | Спрацьовує коли |
|-------|------------------|
| `stock_reorder_alert` | Філамент досяг точки повторного замовлення у прогнозі запасу. |
| `stock_break_alert` | Філамент закінчиться раніше, ніж могло б прибути поповнення. |

Обидві типово вимкнені на провайдерах і в Telegram-чатах. Повідомлення називає філамент повністю — матеріал, підтип і **колір** — у заголовку й тексті, тож Black і White одного продукту — це два різні повідомлення. Філамент перебуває в одному з двох станів, і закінчення — терміновіша новина: отримувач, підписаний на обидві події, отримує лише повідомлення про ризик закінчення, а отримувач, підписаний **лише на повторне замовлення**, отримує повідомлення про замовлення й для філаменту, який уже в стані закінчення. Обидва повідомлення про один філамент не отримує ніхто.

Філамент, у якого всі котушки заархівовано, не «закінчується» — він закінчився. Його рядок лишається в прогнозі 90 днів, але сповіщення поводяться з ним інакше:

- поки той самий матеріал, підтип і колір є на полиці під **іншим брендом**, про нього не надсилається нічого — ферма просто перейшла на інший бренд;
- інакше про нього повідомляють **один раз** — **Закінчився**, окремим текстом (шаблон `stock_depleted_alert`), тим самим отримувачам, що й ризик закінчення. Ризик закінчення повторюється раз на добу; закінчений філамент — ні. Повідомлення прийде знову, лише якщо він закінчиться ще раз після того, як його котушка — будь-якого бренду — знову з'явилась на полиці.

Якщо колір зник назавжди і навіть одне повідомлення не потрібне, вимкніть сповіщення для його рядка в прогнозі.

**Користувач / система:**

| Подія | Спрацьовує коли |
|-------|------------------|
| `user_created`, `password_reset` | Account-management емейли (HTML + plain). |
| `user_print_start` / `user_print_complete` / `user_print_failed` / `user_print_stopped` | Per-user email коли користувач — власник друку. |
| `test` | Тест-надсилання з редактора провайдера. |
| `external_app_message` | Інша програма надіслала повідомлення через API — див. [Повідомлення від зовнішніх програм](#external-app-messages). |

### Наближається пауза { #pause-coming-up }

**Наближається пауза** (`pause_coming_up`) попереджає, що поточний друк от-от дійде до паузи, доданої у слайсері, — час іти до принтера з магнітами, гайками чи наступним філаментом. Ідеться про ті самі паузи, які картка принтера показує як [наступну паузу слайсера](monitoring.uk.md#next-pause), і подія лише інформує: на принтер нічого не надсилається.

- **Типово вимкнено всюди** — у кожного провайдера, у кожному Telegram-чаті та в підписках інбоксу (це подія рівня *info*). Увімкни там, де вона потрібна.
- **Один раз на кожну паузу кожного друку.** Файл із трьома паузами дає три повідомлення, по одному перед кожною. Повторний друк того самого файла — це інший друк, і про нього попереджають знову.
- **Коли надсилається** — це **Випередження попередження про паузу** в **Налаштування → Друк**: 0–120 хвилин, типово 5. Коли є оцінка часу — стандартна швидкість і файл із позначками часу — подія надсилається, щойно оцінка не перевищує випередження. Без неї подія надсилається, коли друк доходить до шару перед паузою. **0 вимикає подію.**
- **Після перезапуску BamDude** друк, знайдений знову вже всередині часу випередження, пропускає це одне попередження — воно могло піти ще до перезапуску, а двічі жодне попередження не надсилається.

Типове повідомлення:

```
Наближається пауза
Bambu X1C: Benchy
Пауза на шарі 42/250 — приблизно через 5 хв
```

Без оцінки часу остання частина звучить як *на наступному шарі*.

### Результат не перевірено { #result-not-checked }

**Результат не перевірено** (`print_outcome_unchecked`) нагадує, що завершений друк досі несе [позначку **Не перевірено**](archiving.uk.md#checking-a-prints-result) — ніхто не записав його брак і не натиснув **Без браку**. Подія лише інформує: ні друк, ні кількість браку, ні чергу вона не зачіпає.

- **Типово вимкнено всюди** — на кожному провайдері, у кожному Telegram-чаті і в підписках вхідних (це подія рівня *info*). Увімкніть там, де вона потрібна.
- **Один раз на друк.** Нагадування, яке не вдалося доставити, не надсилається вдруге, а друк, результат якого вже перевірено, не отримує жодного.
- **Коли надсилається** — це **Нагадування про неперевірений результат** у **Налаштування → Друк**: скільки хвилин завершений друк може лишатися неперевіреним, типово 60, від 5 хвилин до тижня (10080). Час рахується від моменту завершення друку.
- **Лише завершені друки.** Невдалий, скасований чи калібрувальний друк не буває неперевіреним, тож і нагадування про нього немає.
- **Увімкнення події пізніше не випускає накопичених нагадувань.** Друк, час якого минув, закривається незалежно від того, чи був тоді хтось підписаний.
- **У Telegram** нагадування несе кнопки **Брак…** і **Без браку** для цього друку, і реакція 👍 чи 👎 на нього теж є відповіддю — див. [Telegram-бот → Активні сповіщення](telegram-bot.uk.md#активні-сповіщення).

Типове повідомлення:

```
Результат друку не перевірено
Bambu X1C: Benchy
Завершено 2024-01-15 13:30. Результат ще ніхто не перевірив.
https://bamdude.example/archives?outcome=unchecked
```

Посилання відкриває сторінку Архівів з увімкненим фільтром **Неперевірені**; його немає, коли **Зовнішній URL** у **Налаштування → Мережа** не задано.

### Повідомлення від зовнішніх програм { #external-app-messages }

Інша програма ферми — Home Assistant, скрипт, бот — може повідомити людям ферми щось через канали BamDude: *зникло світло*, *сушарка закінчила*. Вона надсилає один запит, і повідомлення приходить як подія **Зовнішня програма** (`external_app_message`).

- **Хто може надсилати.** Лише API-ключ, створений з позначкою **Надсилати сповіщення як зовнішня програма** (**Налаштування → API-ключі**; за замовчуванням вимкнено), власник якого активний і має право керувати сповіщеннями (`notifications:update` — є в Адміністраторів та Операторів). Із браузера після входу ці повідомлення не надсилаються.
- **Хто отримує.** Вбудовані сповіщення показують його всім за замовчуванням. Провайдери й Telegram-чати отримують його, коли для них увімкнено **Зовнішня програма**, — за замовчуванням вимкнено в обох. Це загальна новина ферми, тож провайдер, обмежений кількома принтерами, теж її отримує.
- **Рівень.** Відправник обирає `info` (за замовчуванням), `warning` або `error`. Рівень фарбує повідомлення у вбудованих сповіщеннях і ставить ℹ️, ⚠️ або 🚨 на початку заголовка в інших каналах.
- **Відправника видно завжди** — назву ключа та його власника: у вбудованих сповіщеннях окремим рядком (**Від: Home Assistant · admin**), в інших каналах останнім рядком повідомлення. Редагування шаблону його не прибирає, тож повідомлення програми не видасть себе за повідомлення BamDude.
- **Що можна надіслати.** Простий текст: заголовок до 120 символів, повідомлення до 2000 і, за бажанням, посилання (лише `http` або `https`), яке вбудовані сповіщення показують як **Відкрити посилання**. Керівні символи прибираються, а `*` замінюється, щоб не вмикати жирний шрифт у Telegram.
- **Як часто.** 20 повідомлень на хвилину з одного ключа. Наступне відхиляється з `429` і заголовком `Retry-After`.

Запит:

```http
POST /api/v1/notifications/external-message
X-API-Key: bd_…
Content-Type: application/json

{"title": "Power lost", "message": "The farm is on battery.", "level": "error", "link": "https://ha.local/lovelace/power"}
```

Відповідь каже, кого повідомлення досягло, — людей, чиї вбудовані сповіщення його прийняли, і провайдерів, яких попросили його надіслати: `{"inbox_recipients": 3, "channels": 2}`.

З Home Assistant — `rest_command` і дія, що його викликає:

```yaml
rest_command:
  bamdude_message:
    url: "http://YOUR_BAMDUDE_IP:8000/api/v1/notifications/external-message"
    method: POST
    headers:
      X-API-Key: !secret bamdude_api_key
    content_type: "application/json"
    payload: '{{ {"title": title, "message": message, "level": level | default("info")} | to_json }}'
```

```yaml
action: rest_command.bamdude_message
data:
  title: "Power lost"
  message: "The farm is on battery."
  level: "error"
```

Типове повідомлення в інших каналах:

```
🚨 Power lost
The farm is on battery.
https://ha.local/lovelace/power

— Home Assistant · admin
```

## :material-priority-high: Пріоритет на подію { #per-event-priority }

ntfy підтримує рівні пріоритету від `1` (мін.) до `5` (терміново). BamDude дає обрати пріоритет **на тип події** на кожному ntfy-провайдері, тож завершений друк не пушитиме на lock-screen, а провал друку — пушитиме:

| Тип події | Рекомендований ntfy-priority | Чому |
|---|---|---|
| `print_complete`, `bed_cooled` | `default` | Інформаційне — прочитається коли зручно. |
| `print_failed`, `printer_error`, `plate_not_empty` | `high` чи `urgent` | Потребує дії. |
| `filament_low`, `maintenance_due` | `default` | Plan-ahead, не interrupt-now. |
| `ams_humidity_high` | `high` | Стосується пластика, який ось-ось у роботу. |

Налаштовується у формі редагування ntfy-провайдера: розділ **Пріоритет події (ntfy)** показує події, на які провайдер підписаний, кожну — зі своїм списком. Кожна подія стартує з `default` (3) — підвищуй лише там, де треба. Pushover натомість бере один пріоритет на весь провайдер (див. [Pushover](#pushover)).

Провайдер [Gotify](#gotify) має такий самий розділ — **Пріоритет події (Gotify)**: п'ять рівнів ідуть до Gotify як `0`, `2`, `5`, `8` і `10`, а подія без рівня — з `5`.

Це незалежне від нижче daily-digest / quiet-hours pipeline'у — quiet-hour-suppressed подія не відсилається жодним priority; активна подія все одно поважає вибраний per-event priority.

## :material-clock: Тихі години і щоденний digest

Форма конфіга залежить від типу провайдера — Telegram-бот окремий випадок.

**Не-telegram провайдери (email / ntfy / pushover / discord / webhook / homeassistant / callmebot / signal / gotify / notify)** тримають обидва налаштування на самому provider-row:

| Налаштування | Де | Ефект |
|---|---|---|
| `quiet_hours_enabled` + `quiet_hours_start` / `quiet_hours_end` | Конфіг провайдера | Події всередині вікна викидаються (не чекають — quiet hours це "мовчати", не "відкласти"). |
| `daily_digest_enabled` + `daily_digest_time` | Конфіг провайдера | Події протягом дня зберігаються в `notification_digest_queue`; коли годинник переходить `daily_digest_time`, BamDude вислає чергу одним digest-повідомленням. Digest виходить у свій час навіть у тихі години провайдера. |

**Telegram (m045)** структурований інакше: бот/provider-row тримає тільки **розклад** (`daily_digest_enabled` + `daily_digest_time`), а per-event opt-in, тихий час і per-chat digest opt-in живуть на кожному рядку `TelegramChat`. Один чат може бути в quiet-годинах, а інший залишатися гучним — обидва живляться одним ботом. Деталі per-chat-полів див. [Налаштування Telegram-бота](telegram-bot.uk.md).

## :material-file-document-edit: Редактор шаблонів

Кожна подія має дефолтний шаблон у `data/notification_templates_{en,uk}.json`. Вкладка Templates під Settings → Notifications дозволяє перевизначити будь-який — тітул + тіло — з MarkdownV2 toolbar і live-прев'ю. Кожен шаблон показує перелік своїх змінних і має прев'ю.

Вкладка Templates групує дефолтні шаблони за призначенням, щоб одним поглядом було видно, який dispatch-шлях кожен з них живить:

| Група | К-ть | Для чого |
|---|---|---|
| **Print events** | 13 | `print_start/complete/failed/stopped/paused/resumed/progress`, `plate_not_empty`, `bed_cooled`, `first_layer_complete`, `pause_coming_up`, `print_outcome_unchecked`, `print_missing_spool_assignment` |
| **Printer status** | 4 | `printer_offline`, `printer_error`, `filament_low`, `maintenance_due` |
| **AMS environmental** | 2 | `ams_humidity_high`, `ams_temperature_high` (також reuse-яться у runtime для AMS-HT-подій) |
| **Sensor alerts** | 5 | `sensor_above_max`, `sensor_below_min`, `sensor_back_in_range`, `sensor_silent`, `sensor_speaking_again` — див. [Датчики середовища](sensors.md) |
| **Print queue** | 7 | `queue_job_added/started/waiting/skipped/failed`, `queue_completed`, `printer_queue_completed` |
| **Job owner emails** | 4 | `user_print_start/complete/failed/stopped` — SMTP-only, шлеться власнику задачі друку |
| **System emails** | 2 | `user_created` (welcome), `password_reset` |
| **Test** | 1 | `test` — для кнопок "Send test" |

Кожна картка несе маленький UPPERCASE-бейдж каналу:

- **Зелений `ALL`** — фан-аут до всіх типів провайдерів (TG / email / ntfy / pushover / discord / webhook / homeassistant / callmebot / signal / gotify / notify). Записи у перших 4 групах.
- **Синій `EMAIL`** — SMTP-only флоу. 4× `user_print_*` job-owner emails плюс `user_created` / `password_reset`.
- **Амбер `TEST`** — внутрішній test-button helper.

Маппінг — це метадані про те, який dispatch-шлях кожен шаблон живить; не зберігаються на рядку, рендеряться зі статичної таблиці у frontend-і.

Підстановка змінних — простий `{plate_holder}` синтаксис (`{printer_name}`, `{filament_grams}`, `{eta}` і т.д.); схема залочена на подію, тож редактор сам попереджає, коли placeholder не резолвиться.

Шаблон вибирається **за мовою отримувача**: Telegram-чат, прив'язаний до оператора з `settings.language=uk`, отримає українське тіло; email до іншого юзера з `settings.language=en` — англійське. Нові ключі додавайте в **обидва** JSON-файли — BamDude постачається лише з en + uk.

## :material-email-newsletter: Приклад Daily Digest

Коли провайдер має `daily_digest_enabled` + `daily_digest_time` встановлене, кожна подія, яка спрацювала за день, кладеться в чергу і об'єднується в одне summary-повідомлення на digest-час:

```
Daily Digest - 5 Events

== Print Complete (3) ==
  09:12 [P1S-01] Print complete: Benchy
  11:40 [X1C-02] Print complete: Phone Stand
  14:05 [P1S-01] Print complete: Cable Clip

== Print Failed (1) ==
  16:31 [X1C-02] Print failed: Prototype v3

== Filament Low (1) ==
  13.04 22:48 [P1S-01] Low filament
```

Події згруповано за типом, у порядку, в якому вони сталися. Кожен рядок — це час, принтер у дужках, якщо подія його має, і заголовок, з яким подію було надіслано. Тому рядки йдуть мовою ваших шаблонів, а заголовок digest-у й назви груп незмінні.

Digest, який не вдалося надіслати, зберігає свої події до наступної спроби; події, старші за 48 годин, відкидаються ненадісланими. Подія, перенесена з попереднього дня, показується з датою, а не лише з часом.

## :material-file-document-edit: Змінні шаблонів

Шаблони підставляють `{variable}`-плейсхолдери. Схема залочена на подію, тож редактор попереджає, коли використано невідомий плейсхолдер. Змінні згруповані за категорією події:

**Print events** (`print_start`, `print_complete`, `print_failed`, `print_stopped`, `print_progress`):

| Змінна | Значення |
|---|---|
| `{printer_name}` (alias `{printer}`) | Display-ім'я принтера |
| `{print_name}` (alias `{filename}`) | Файл, який зараз друкується |
| `{progress}` | % завершення (тільки failed/stopped) |
| `{eta_minutes}` / `{eta}` | Wall-clock час завершення |
| `{estimated_time}` | Прогнозована тривалість друку (напр. `1h 23m`) |
| `{duration}` | Реальний elapsed-час друку |
| `{filament_used_g}` (alias `{filament_grams}`) | Загальні грами (scaled by progress для фейлів) |
| `{filament_details}` | Per-spool breakdown (напр. `AMS-A T1 PLA: 15.2g`) |
| `{material}` | Aggregate material name |
| `{reason}` | Причина фейлу (тільки failed/stopped) |
| `{finish_photo_url}` | URL camera-snapshot (див. нижче) |

**Printer events** (`printer_offline`, `printer_error`):

| Змінна | Значення |
|---|---|
| `{printer_name}` | Display-ім'я принтера |
| `{error_code}` (alias `{error_type}`) | HMS error code — повний код із чотирьох груп (`0500-0600-0002-0070`) для збою зі списку HMS принтера, коротка форма `XXXX_XXXX` для `print_error` |
| `{error_message}` (alias `{error_detail}`) | Людино-читабельний опис (BamDude перекладає каталог 853 кодів) |

**AMS events** (`ams_humidity_high`, `ams_temperature_high`, `filament_low`, `print_missing_spool_assignment`):

| Змінна | Значення |
|---|---|
| `{ams_id}` | AMS-юніт (`AMS-A`, `AMS-B`, …) |
| `{slot}` | Tray index (`T1`–`T4`) |
| `{material}` | Матеріал, призначений на слот |
| `{remaining_percent}` | Залишок філаменту (`filament_low`) |
| `{humidity}` | % вологості (humidity events) |
| `{missing_slots}` | Comma-separated лейбли слотів (`A1, A3`) для `print_missing_spool_assignment` |
| `{missing_slot_details}` | Per-slot breakdown з очікуваним профілем (`- A1: PLA Basic`) |

**Попередження про паузу** (`pause_coming_up`):

| Змінна | Значення |
|---|---|
| `{printer}` | Назва принтера |
| `{filename}` | Файл, який зараз друкується |
| `{layer}` | Шар, на якому пауза |
| `{total_layers}` | Загальна кількість шарів друку |
| `{time_to_pause}` | Готова фраза: `приблизно через 5 хв` або `на наступному шарі`, коли оцінки часу немає |
| `{minutes}` | Оцінка як саме число; порожньо, коли оцінки часу немає |

**Результат не перевірено** (`print_outcome_unchecked`):

| Змінна | Значення |
|---|---|
| `{printer}` | Назва принтера |
| `{filename}` | Назва друку |
| `{finished_at}` | Коли друк завершився, у часовому поясі сервера (`2024-01-15 13:30`) |
| `{archive_url}` | Посилання на сторінку Архівів з увімкненим фільтром **Неперевірені**; порожнє без зовнішнього URL |

**Події інвентаря** (`stock_reorder_alert`, `stock_break_alert` і `stock_depleted_alert` — текст, яким повідомляють про закінчений філамент):

| Змінна | Значення |
|---|---|
| `{filament}` | Філамент, про який сповіщення, — матеріал, підтип і колір однією назвою |
| `{material}`, `{subtype}`, `{color}` | Ті самі три частини окремо |
| `{brand}` | Бренд |
| `{stock_g}` | Залишок, грами |
| `{rate_g_day}` | Темп витрати, грамів на день |
| `{days_left}` | На скільки днів вистачить запасу |
| `{lead_time_days}` | Термін постачання в днях (`stock_break_alert` і `stock_depleted_alert`) |

**Зовнішні програми** (`external_app_message`):

| Змінна | Значення |
|---|---|
| `{title}` | Заголовок, який надіслала програма |
| `{message}` | Її текст |
| `{level}` | `info`, `warning` або `error` |
| `{level_icon}` | ℹ️, ⚠️ або 🚨 |
| `{link}` | Її посилання; порожнє, якщо його немає |
| `{sender}` | Ключ і його власник — код однаково дописує цей рядок до кожного повідомлення |

**Job owner emails** (`user_print_start`, `user_print_complete`, `user_print_failed`, `user_print_stopped`):

| Змінна | Значення |
|---|---|
| `{username}` | Власник друку |
| `{printer}` | Назва принтера |
| `{filename}` | Надрукований файл |
| `{finish_photo_url}` | Посилання на фото завершення (completed / failed / stopped; див. нижче) |

**Common для будь-якої події:** `{timestamp}`, `{app_name}` (завжди `"BamDude"`).

Натисни **Reset to default** у редакторі, щоб відновити оригінальний шаблон з `notification_templates_{en,uk}.json`.

### Фото у сповіщеннях

Події, що мають кадр камери, несуть його: фото завершення на завершенні й провалі друку, знімок першого шару, кадр, який позначив детектор, у **Виявлення збою ШІ**, кадр, за яким перевірка ухвалила рішення, у **Стіл не порожній**, і знімок разом із помилкою принтера.

- **Більшість каналів отримує саму картинку** — Telegram, Discord, Pushover, ntfy, Signal і webhook-и generic-формату. Email вбудовує фото завершення, коли його шаблон містить `{finish_photo_url}` (див. нижче).
- **Home Assistant, Bark, Gotify, Notify! і webhook-и формату Slack / Mattermost отримують посилання** на копію цієї однієї картинки, бо ці сервіси завантажують її самі. Home Assistant отримує його лише з власним сервісом `notify.*`, як `data.image` — якщо твоє поле **Data (JSON)** не задає власний `image`. Bark показує її як іконку сповіщення, Gotify — великою картинкою у своєму застосунку для Android, Notify! — картинкою сповіщення (лише HTTPS-посилання; одержувачі в браузері й групи її не отримують). Для цього потрібне налаштування **External URL**; без нього ці канали отримують лише текст.
- **Прикріплювати фото** — цей перемикач є в кожного каналу, типово увімкнений. Вимкнений — канал отримує лише текст.

Копія, на яку веде посилання, має адресу, яку неможливо вгадати, відкривається за самим лише посиланням і перестає працювати через 3 дні. Посилання відкриває лише цю одну картинку — не архів і не камеру.

### Finish Photo URL

Плейсхолдер `{finish_photo_url}` кладе camera-snapshot готової плити в сповіщення про завершення / провал. Потребує доступної external URL:

1. **Налаштування** → **Мережа** → **Зовнішній URL** — постав адресу, до якої отримувачі мають доступ (напр. `https://bamdude.example.com` чи `http://192.168.1.100:8000`)
2. Налаштування auto-detect-иться з браузера, коли вперше відкриваєш System settings
3. Відредагуй шаблон і додай `{finish_photo_url}` куди хочеш фото

!!! tip "Email вшиває фото inline, не лише посилання"
    Для **email**-провайдерів, коли підставлений `{finish_photo_url}` присутній у тілі **і** finish-фото справді зроблено, BamDude шле лист як `multipart/related` зі вбудованим inline JPEG (через `Content-ID`, на який посилається HTML-частина) — фото видно прямо в тілі листа, а не як голе посилання. Plain-text альтернатива й далі несе клікабельний URL для text-only клієнтів. Коли шаблон не містить `{finish_photo_url}` (або фото немає), використовується звичайний single-part text-лист — без несподіваного attachment-а. Не-email канали (WhatsApp / webhook / …) й далі отримують посилання — тому External URL нижче має бути досяжним.

!!! note "External URL — обов'язкова умова"
    Без сконфігурованого External URL посилання не має адреси, до якої міг би дістатися зовнішній сервіс. Посилання веде не на власне фото архіву — те потребує входу, як і кожна інша картинка архіву, — а на окрему копію цього одного фото з адресою, яку неможливо вгадати, і вона перестає працювати через 3 дні. До того часу картинку відкриє кожен, хто має посилання, тож не поширюйте посилання зі сповіщень, якщо на готовій плиті є чутлива робота.

!!! info "Доставка сповіщень про старт і завершення"
    Друк із черги надсилає сповіщення про старт один раз на запуск, а захоплення фото та доставка повідомлення завершуються після очищення живого стану друку. Збій камери все ще може залишити повідомлення без фото. Старт нового друку скасовує право попереднього знімати принтер або виконувати відкладені дії після завершення.

## :material-bell-off: Quick Disable

Глобальний mute-toggle живе у sidebar-і — клік по іконці дзвоника гасить **усі** вихідні сповіщення на **усіх** провайдерах, поки не клікнеш ще раз. Корисно під maintenance-вікно, demo-прогон чи галасливу міграцію, коли не хочеться флудити team-чат.

Toggle не видаляє digest-и-в-роботі — події, що впали в digest-чергу до mute, все одно вийдуть на наступний `daily_digest_time`. Щоб затримати digest, відключи daily-digest на самому провайдері.

## :material-printer: Per-Printer фільтрація

Кожен не-telegram провайдер має скоуп принтерів — **Всі** (default), один або будь-яка підмножина, відмічена чекбоксами на формі провайдера. Події з принтерів поза вибраною множиною ніколи не доходять до цього провайдера, незалежно від event-toggle-ів. **Для Telegram скоуп живе на кожному чаті** (див. [Telegram Bot → Скоуп принтерів](telegram-bot.md)) — і там він обмежує й самого бота: списки, камери, чергу та керування. Корисні патерни:

- Один Discord-webhook на майстерню — кожен прив'язаний до її принтерів
- "VIP printer" Telegram-чат, прив'язаний до однієї production-одиниці, що генерує дохід
- Maintenance-only ntfy провайдер, прив'язаний до принтерів, у яких підходять заміни фільтрів / ременів

Новини, що не називають принтера, діляться на два види. Загальнофермові — завершення черг усієї ферми, сповіщення про запас, тестові повідомлення — доходять до кожного провайдера й чату, обмеженого чи ні. Два види до отримувача, обмеженого окремими принтерами, **не** доходять:

- зведення **Авточерга потребує уваги** (`queue_job_waiting`) — воно описує перешкоди всієї ферми й не називає принтера, тож іде лише необмеженим провайдерам, необмеженим Telegram-чатам і у вхідні;
- сповіщення **датчика приміщення чи сховища** — того, що стоїть на локації, а не на принтері. Сповіщення датчика, розміщеного на принтері, йде за скоупом цього принтера.

Провайдер чи чат, що має їх отримувати, слід лишити на **Всі** принтери.

## :material-inbox: Центр сповіщень

Сповіщенню не обов'язково йти назовні. **Дзвоник** у sidebar-і відкриває персональний центр сповіщень із трьома вкладками, і **вхідні наповнюються незалежно від того, чи налаштований хоч один провайдер** — тож інсталяція без жодного провайдера все одно має куди покласти алерт про власне залізо. У цьому й суть: провайдери — це те, як сповіщення доходить до твого телефона, а вхідні — як воно доходить до того, хто зайшов в інтерфейс.

Прочитане і непрочитане — **у кожного своє**. Один оператор, що відкрив алерт, не гасить його для решти. Це і є різниця між вхідними і спільним логом: з подією розбирається кожен, хто на неї підписаний.

### Вхідні

Події, на які ти підписаний, найновіші згори. Непрочитані рядки помічені; клік по рядку позначає його прочитаним і розгортає повний текст. Кожен рядок несе:

| У рядку | Що показує |
|---|---|
| Рівень | **info**, **warning** або **error** |
| Принтер | з якого принтера прийшла подія |
| Давність | скільки часу тому це сталося |

Список звужують чотири фільтри — **рівень**, **принтер**, **лише непрочитані** і **період**: останні 24 години, 7 днів, 30 днів або весь час. Довга історія вантажиться сторінками через кнопку **Show more**, а не вся одразу.

!!! warning "Mark all read і Clear діють на фільтр, а не на всі вхідні"
    Обидві кнопки застосовуються рівно до того, що зараз вибрано фільтрами. З *error* + *один принтер* + *останні 7 днів* **Clear** видалить саме ці рядки й не зачепить решту — а без жодного фільтра видалить усе. **Clear** саме видаляє, тому спершу питає підтвердження. Рядки також можна видаляти по одному просто з рядка.

### Підписки

Чекбокс на кожну подію, згруповані за областями — друки, принтери, філамент, AMS, черга, інвентар, сенсори, — і поряд із кожною вказано її рівень, тож видно ціну підписки ще до того, як ти поставиш галочку.

**За замовчуванням людина отримує лише warning-и й error-и.** Вхідні мовчать, доки справді щось не потребує уваги, а кнопка **Reset to defaults** повертає рівно цей стан після будь-яких експериментів. Кожна зміна зберігається одразу — Save-кнопки, яку можна забути натиснути, тут немає.

Підписки належать людині, а не фермі: два оператори на одній інсталяції можуть стежити за зовсім різним, і вибір одного ніяк не змінює вхідні іншого.

### Email

Чотири per-user email-перемикачі — що і коли вони шлють, див. [Per-User Email сповіщення](#per-user-email-сповіщення) нижче.

Вкладка з'являється, тільки якщо увімкнено Advanced Authentication, увімкнено майстер-перемикач **User Notifications** і в тебе є право `notifications:user_email`.

### Лічильник непрочитаного

Дзвоник у sidebar-і несе живий лічильник непрочитаного. Він оновлюється по тому самому WebSocket-з'єднанню, яким уже користується решта інтерфейсу, тож нова подія з'являється на дзвонику без перезавантаження сторінки і без полінгу. На вузьких екранах компактний хедер несе той самий дзвоник і той самий лічильник.

### Дозвіл

Центр сповіщень вимагає права `notifications:inbox`.

!!! warning "Нотатка до оновлення — кастомна група його сама не отримає"
    **Administrators**, **Operators** і **Viewers** отримують `notifications:inbox` під час оновлення. Група, яку ти зробив руками, — **ні**: оновлення не дописує права у групи, зібрані вручну. Доки адміністратор не видасть право, учасники такої групи втрачають сторінку цілком, **разом із per-user email-перемикачами, які в них були раніше**. Пройдись по своїх кастомних групах одразу після оновлення.

### Зберігання

**Settings** → **Data Management** містить **Inbox notifications (days)**.

| Налаштування | Типово | Діапазон |
|---|---|---|
| Inbox notifications | **30 днів** | 1–365 днів |

Щоденне прибирання видаляє все, старше за вікно, незалежно від того, прочитане воно чи ні — вхідні, які ніхто не відкриває, не ростуть вічно. Видалення користувача забирає його вхідні разом із ним.

## :material-email-outline: Per-User Email сповіщення { #per-user-email-сповіщення }

Окремо від системи провайдерів вище — BamDude вміє писати email **власнику** друку напряму, коли той завершиться / провалиться / зупиниться — корисно у shared / multi-tenant deployment-ах, де кожен юзер хоче пошту своїх друків в особисту скриньку.

### Вимоги

- Authentication увімкнена (вона завжди увімкнена)
- SMTP налаштовано в **Налаштування** → **Автентифікація** → **Email автентифікація** (картка **Конфігурація SMTP**)
- **Settings** → **Notifications** → **User Notifications** перемкнуто on
- У користувача є email на акаунті
- Користувач має право `notifications:user_email` (за замовчуванням у **Administrators** + **Operators** — див. [Authentication](authentication.uk.md))
- Користувач має право `notifications:inbox` — перемикачі є вкладкою [центру сповіщень](#центр-сповіщень), і без цього права сторінку взагалі не відкрити

### Підтримувані події

| Подія | Спрацьовує на |
|---|---|
| `user_print_start` | Друк користувача стартує |
| `user_print_complete` | Його друк завершився успішно |
| `user_print_failed` | Його друк збився |
| `user_print_stopped` | Він сам скасував свій друк |

Лист про завершений друк показує фото завершення, коли його зроблено, а шаблони completed / failed / stopped можуть розмістити його через `{finish_photo_url}`.

Завершення друку, яке BamDude не може зіставити з жодним своїм друком, листа нікому не надсилає: повідомляються лише провайдери сповіщень, підписані на подію.

Кожен користувач вмикає й вимикає ці чотири події окремо на вкладці **Email** свого [центру сповіщень](#центр-сповіщень) — того самого дзвоника в sidebar-і. Майстер-перемикач **User Notifications** — у operator-а / admin-а під **Settings** → **Notifications**.

## :material-bed: Як пропустити подію, що вимагає дії, крізь ніч

Деякі події зупиняють ферму, доки хтось не втрутиться:

- **`plate_not_empty`** — перед стартом queue-job-а зловили непорожній стіл, і диспетч тепер на паузі. Проспати — означає, що черга стоятиме до пробудження.
- **`bed_cooled`** — стіл упав нижче налаштованого порога (типово 35 °C) після друку, тобто деталь можна знімати.
- **Порогові алерти сенсорів** — у кімнаті надто холодно чи надто волого для філаменту, який зараз друкується.

!!! warning "Тихі години — на провайдер, а не на подію"
    Обходу на рівні події немає. Провайдер усередині свого тихого вікна відкидає **все**, зокрема й три пункти вище, — тож провайдер, тихий із 22:00, не скаже тобі, що черга стала о 01:00.

    Замість цього маршрутизуй: заведи для подій, що вимагають дії, **окремий провайдер** із вимкненими тихими годинами, а балакучі (прогрес, старт друку) лиши на тому, який спить. На iOS найсильніший варіант цього — провайдер [Bark](#bark-ios) на рівні **Critical**: він проходить ще й крізь Silent mode і Focus.

**Щоденний digest** — окремий opt-in канал, і він нічого не затримує: кожне сповіщення надсилається тоді, коли сталося, а digest — це додаткове зведення зверху. Він надсилається у свій заданий час навіть у тихі години провайдера.

## :material-check-circle: Тестування

Збережений провайдер має кнопку **Send Test**. Для звичайних провайдерів клік запускає синтетичну подію через повний pipeline (template render, quiet-hour gate, priority mapping, transport-specific wrap), тож результуюче повідомлення — точне прев'ю того, як виглядатимуть реальні події, не stripped-down "hello world". Telegram використовує власні активні чати: тест одразу йде кожному активному чату, прив'язаному до цього бота, незалежно від підписок на події, scope принтерів чи тихих годин. Це перевірка доставки кожному одержувачу, а не симуляція події ферми.

Re-test після редагування шаблонів, зміни priority чи transport-level полів типу SMTP credentials. Тест обходить digest-чергу (завжди шлеться одразу), тож не треба чекати digest-час, щоб побачити результат.
