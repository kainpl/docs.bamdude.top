# Slicer API (серверний слайсинг)

BamDude вміє слайсити STL і unsliced-3MF файли **на сервері**, спілкуючись з контейнерним **OrcaSlicer** чи **BambuStudio** sidecar по HTTP. Кидаєш файл у бібліотеку, тиснеш **Slice**, обираєш модель принтера + філамент-профіль — і за хвилину готовий `.gcode.3mf` лежить у бібліотеці. Без ноутбука, без слайсера-проксі, без перетягування файлів.

Опційно: жоден слайсер не їде в самому BamDude-образі. Sidecar запускається окремо (Docker Compose рецепт нижче), а BamDude'у кажеш, де він живе.

---

## :material-architecture: Архітектура

```
                ┌───────────────┐
   Файл бібл-и  │   BamDude     │   STL / 3MF (settings)
  ──────────►   │   backend     │ ──────────────────►
                │               │                          ┌──────────────────┐
                │  slicer_api   │   POST /slice            │ slicer-api       │
                │  HTTP bridge  │ ──────────────────►      │ sidecar          │
                │               │                          │   OrcaSlicer чи  │
                │               │   GET /slice/progress    │   BambuStudio    │
                │               │ ◄──────────────────      │   CLI всередині  │
                │               │                          │                  │
                │               │   .gcode.3mf bytes       │                  │
                │               │ ◄──────────────────      │                  │
                │               │                          └──────────────────┘
                │  Library row  │
                │  + archive    │
                └───────────────┘
```

Bridge тримає sliced-output **у бібліотеці** (чи в архіві, залежно з якої сторінки слайсив), записує кожен параметр, що пішов у слайсинг, і чисто фейлиться, якщо sidecar offline чи відмовив файл.

## :material-package-variant: Підтримувані sidecar'и

| Слайсер | Контейнер | Примітки |
|---------|-----------|----------|
| **OrcaSlicer** | Open-source community-image | Рекомендований — активно розвивається, широка підтримка принтерів/пластиків. |
| **BambuStudio** | Офіційний Bambu Lab | Коли треба байт-в-байт повтор результату десктопного Bambu Studio. |

Обидва говорять одним і тим самим `/slice` HTTP API. Можеш запускати один з них або обидва одразу; активний(і) обираєш у **Settings → Profiles → Slicer API**.

## :material-docker: Setup через Docker Compose

В репо BamDude уже шипиться готовий стек у [`slicer-api/`](https://github.com/kainpl/bamdude/tree/main/slicer-api) — найпростіший спосіб через нього:

```bash
git clone https://github.com/kainpl/bamdude.git
cd bamdude/slicer-api/
cp .env.example .env       # опційно — pin версії слайсерів / порти

# Обери рівно один:
docker compose --profile orca   up -d   # тільки OrcaSlicer    (host port 3003)
docker compose --profile bambu  up -d   # тільки BambuStudio   (host port 3001)
docker compose --profile all    up -d   # обидва
```

Голий `docker compose up -d` (без profile) не запустить нічого — треба явно вказати `--profile orca`, `--profile bambu` чи `--profile all`. Потім у BamDude → **Settings → Profiles → Slicer API** заповни URL для слайсерів, які запустив (`http://localhost:3003` для Orca, `http://localhost:3001` для BambuStudio).

!!! warning "Docker Desktop 4.71 — обхід для першого білда"
    Docker Desktop 4.71 (engine 29.4.1 / compose v5.1.x / buildx 0.33.x-desktop) має зламаний `buildx bake` compose-bridge: `docker compose build` миттєво падає з `failed to execute bake: exit status 1` без жодних деталей, незалежно від форми profiles. `COMPOSE_BAKE=false` НЕ вимикає bake на цій версії.

    **Обхід для першого білда** — форснути legacy classic builder; image тоді кешується і `compose up -d` перевикористовує його:

    ```bash
    # bash / zsh
    DOCKER_BUILDKIT=0 COMPOSE_DOCKER_CLI_BUILD=0 \
      docker compose --profile all build
    docker compose --profile all up -d
    ```

    ```powershell
    # PowerShell
    $env:DOCKER_BUILDKIT = "0"; $env:COMPOSE_DOCKER_CLI_BUILD = "0"
    docker compose --profile all build
    $env:DOCKER_BUILDKIT = $null; $env:COMPOSE_DOCKER_CLI_BUILD = $null
    docker compose --profile all up -d
    ```

    Або викликай buildx напряму (modern BuildKit, паралельно, швидше):

    ```bash
    docker buildx bake -f docker-compose.yml orca-slicer-api
    docker buildx bake -f docker-compose.yml bambu-studio-api
    docker compose --profile all up -d
    ```

    Старіші релізи Docker Desktop (4.70 і нижче) та Docker CE на Linux баг не зачепив — env vars не потрібні.

### Запустити sidecar(и) на іншій машині

Якщо BamDude-сервер сам не може крутити sidecar-контейнери (resource-ліміти, немає Docker, тощо) — постав sidecar(и) на окремій машині й вкажи їхні URL у BamDude. Той самий `slicer-api/docker-compose.yml` з репо BamDude використовуй на хості sidecar'ів, потім у `Settings → Profiles → Slicer API` встанови URL'и `http://<sidecar-host>:3003` / `:3001` замість `localhost`. Sidecar не має auth — тримай у trusted network (LAN, Tailscale, WireGuard).

Можеш також override'нути env-дефолти, які BamDude читає на старті: `SLICER_API_URL` (default `http://localhost:3003`) і `BAMBU_STUDIO_API_URL` (default `http://localhost:3001`). UI-поля URL мають пріоритет, якщо встановлені.

### Оновлення sidecar'ів { #updating-the-sidecars }

Перезбирати контейнери є дві причини, і друга не потребує зміни версії:

- **Новіший слайсер** — зміни `ORCA_VERSION` / `BAMBU_VERSION`.
- **Новіший sidecar** — HTTP-обгортка навколо слайсера збирається разом із контейнером, тож вона така ж стара, як твоя остання збірка, хоч якому BamDude служить. BamDude питає кожен sidecar про версію його коду, і коли запущений старіший, ніж потрібно BamDude, діалог нарізки каже про це під картками слайсерів: *«Контейнер слайсера старіший, ніж потрібно цій версії BamDude: …»* — разом із командами нижче. Нарізка тим часом працює далі, наскільки старіший контейнер уміє: у списках може бракувати частини профілів, а профіль, який слайсер не може розв'язати, нарізається на вбудованих типових значеннях слайсера замість [відмови](#failure-modes).

В обох випадках — перезбери й перезапусти:

```bash
cd slicer-api
docker compose --profile all build --no-cache
docker compose --profile all up -d
```

Якщо тримаєш лише один слайсер — підстав `orca` чи `bambu` замість `all`. Прапорець `--profile` потрібен в обох командах: без нього Compose пропускає обидва сервіси, звітує про успіх, а старий контейнер працює далі.

Дві пастки, обидві мовчазні:

- **Контекст збірки — GitHub-репозиторій sidecar'а** (`https://github.com/kainpl/orca-slicer-api.git#bamdude/profile-resolver`), а не тека на твоєму диску. Перезбірка бере код sidecar'а звідти; саме `--no-cache` змушує Docker завантажити його — і сам слайсер — заново, а не взяти шари попередньої збірки.
- **Версія слайсера записана двічі** — як типове значення в `docker-compose.yml` і в `.env` — і перемагає `.env`. Файл `.env`, скопійований зі старішого `.env.example`, і далі збирає старіший слайсер, хоч який новий compose-файл; змінюй обидва.

## :material-cog: Settings → Profiles → Slicer API

| Опція | Що робить |
|-------|-----------|
| **Preferred slicer** | `OrcaSlicer` чи `Bambu Studio`. Sidecar за замовчуванням для server-side (in-app) слайсингу. Діалог нарізки й обидві сторінки [калібрування філаменту](filament-calibration.md#choosing-presets) показують картки **Нарізати в**, щоб його перевизначити, — вибір запам'ятовується для кожного файлу в діалозі нарізки й для кожного принтера в калібруванні (у localStorage браузера). |
| **Enable server-side slicing** (`use_slicer_api`) | Master-тоглер. Коли off — кнопка Slice пропадає з File Manager, слайсинг падає на open-in-desktop-slicer через URI scheme. |
| **OrcaSlicer API URL** (`orcaslicer_api_url`) | URL OrcaSlicer-sidecar'а — наприклад `http://localhost:3003` для дефолтного compose-рецепту. Порожнє = використати `SLICER_API_URL` env-дефолт. |
| **BambuStudio API URL** (`bambu_studio_api_url`) | URL BambuStudio-sidecar'а — наприклад `http://localhost:3001`. Порожнє = `BAMBU_STUDIO_API_URL` env-дефолт. |
| **Slicer stall timeout** (`slicer_stall_timeout_minutes`) | У **Settings → General → Slicer**. Хвилин чекати **без жодного прогресу** від sidecar'а. Типово **15**, діапазон 1–240. Деталі нижче. |

!!! info "Stall timeout — це не обмеження на те, скільки може різатися модель"
    Поки триває нарізка, BamDude раз на секунду питає sidecar про прогрес — саме це
    живить toast із відсотками. **Годинник скидається на кожному оновленні
    прогресу**, тож важка модель, яка продовжує звітувати, дорізається до кінця
    хоч скільки часу, і чекання завершує лише справжня тиша.

    На старішому sidecar'і, який не вміє звітувати про прогрес, судити про
    живість нічим — тому те саме число обмежує **загальний** час нарізки.

    Sidecar, який узагалі не приймає з'єднання, і далі одразу позначається як
    недоступний.

Desktop-кнопка **Open in Slicer** керується окремим, незалежним налаштуванням — **Settings → Slicer → Open in Slicer** — dropdown'ом, що за замовчуванням стоїть на **Same as API slicer**. Вкажи інший слайсер, щоб, наприклад, слайсити через Bambu Studio sidecar, а файли відкривати локально в OrcaSlicer (чи навпаки); наявні налаштування не змінюються, поки ти сам не вибереш інше значення.

Передача йде посиланням, а через посилання два слайсери приймають різне: **Bambu Studio бере лише 3MF** — STL чи STEP за посиланням він відхиляє ще до завантаження, — а **OrcaSlicer бере 3MF, STL і STEP**. Тож меню файлу пропонує Open in Slicer лише для файлу, який налаштований слайсер прийме, а 3D-перегляд відкриває STL в OrcaSlicer (називаючи його на кнопці), коли налаштований Bambu Studio.

Preset-tiers (Imported/Local → Orca Cloud → Bambu Cloud → Standard) backend перелічує автоматично у момент слайсингу — per-install setting не потрібен, див. "Слайсинг файлу" нижче.

## :material-cursor-default-click: Слайсинг файлу

З **File Manager**: меню дій на STL / 3MF / STEP / STP файлі → **Slice**.

Відкривається Slice-modal з трьома preset-dropdown'ами:

- **Профіль принтера** — з уніфікованого preset-listing'а. Кожен запис прийшов з одного з чотирьох tier'ів у фіксованому порядку пріоритету й **без dedup між tier'ами** (`local` → `orca_cloud` → `cloud` → `standard`): `local` (твої імпортовані/локальні `.json`-профілі), `orca_cloud` (per-user Orca Cloud-пресети), `cloud` (per-user Bambu Cloud-пресети), `standard` (bundled-defaults у sidecar'і). Оскільки dedup'у немає, однойменний пресет у двох tier'ах перелічується по разу в кожному — він не ховається лише через те, що інший tier має пресет із таким самим ім'ям. Dropdown групує записи за джерелом — див. [Списки профілів](#preset-lists). За замовчуванням обирається принтер, під який готувався вихідний 3MF (якщо такий профіль доступний). Інакше діалог бере профіль принтера із соплом 0.4 мм з усіх списків — що б не показували фільтри нижче, — далі з будь-яким іншим соплом; голий запис моделі на кшталт `Bambu Lab A1`, що не називає сопла, сам ніколи не обирається.
- **Профіль процесу** — ті самі чотири tier'и, але **відфільтровані під обраний принтер**: профілі для інших принтерів зсуваються в кінцеву групу **«Інші принтери»** замість того, щоб зникати, а профілі без інформації про принтер лишаються в основному списку (ніколи не ховаються). За замовчуванням — process, під який готувався 3MF, якщо він сумісний; інакше сумісний, найближчий до висоти шару 0.20 мм («Standard» самого слайсера), а не перший за абеткою — який у найменуванні Bambu завжди найтонший і найповільніший. Зміна принтера перевибирає автоматично підібраний process, якщо той більше не підходить; process, який обрав ти сам, [лишається](#explicit-choice).
- **Профіль філаменту** — один dropdown на кожен слот філаменту, **який декларує проєкт**, а не лише на ті, якими малює ця плита; фільтрація та сама (сумісні профілі спершу, група «Інші принтери» в кінці). Слот стартує з профілю філаменту, який для нього називає сам 3MF-проєкт, — коли цей профіль є у списках, підходить вибраному принтеру і має матеріал плити; якщо профіль із такою назвою є в кількох джерелах, береться той, що з того самого джерела, що й вибраний профіль принтера. Інакше modal pre-pick'ає найкращий match per-slot за filament-metadata вихідного 3MF: профіль **базового матеріалу** слоту (PLA, PETG, ABS… — тип, який заявляє профіль, а не конкретний бренд чи родина профілів; група PA-CF / PA12-CF / PAHT-CF рахується як одна, як і під час друку), точний тип попереду еквівалентного, колір розв'язує нічию, несумісні з принтером — нижче. Профіль іншого матеріалу обирається лише коли більше нічого немає — і тоді той, що підходить вибраному принтеру, іде попереду зробленого для іншого принтера, — а профіль, який обрав **ти** — вручну чи з пайплайна, — ніколи не замінюється через матеріал, тож нарізати модель із позначкою PLA у PETG — твоє рішення. Один клік **Slice** зазвичай робить правильне для multi-color jobs. Біля кожного dropdown стоїть контрол **кольору** — колір, яким друкується цей слот; він записується в нарізаний файл, тож його мініатюра й діалог друку показують саме його. Початково це колір, яким плиту задумав дизайнер, або типовий зелений слайсера для джерела без кольору (STL); постав колір котушки, яку заправиш. Жоден слайсер не зберігає колір у профілі філаменту, тож без цього кожен нарізаний файл виходив зеленим Bambu. Це запис, а не вимога: діалог друку й далі дає зіставити слот із котушкою будь-якого кольору.

    !!! warning "Чому показані всі декларовані слоти, навіть невживані"
        Слайсер прив'язує цей список **за позицією**. Візьми модель, яка декларує чотири
        філаменти, але малює лише слотом 4 — типова форма з MakerWorld. З одним
        dropdown твій вибір потрапляв би у **слот 1**; а слот 4,
        яким модель насправді друкує, різався б з тим, що там лишив автор. Друк
        виходив би не з того матеріалу, і ніщо на екрані на це не натякало б.

        Слоти, яких ця плита не використовує, показані сірими (див. нижче), тож
        вибір філаменту для слота 4 виставляє саме слот 4.

    Діалог **Print** свідомо влаштований інакше: він питає, які котушки потрібні
    завданню, і йому потрібна вузька відповідь — інакше він змушував би зарядити
    три котушки, яких друк ніколи не торкнеться.

Modal кешує cloud- і standard-preset-listing'и на кілька хвилин, тож якщо ти видалиш чи перейменуєш пресет у Bambu Studio / Bambu Handy — він може ще якийсь час висіти в dropdown'ах. Контрол **Refresh** на списку пресетів одразу тягне свіжі listing'и. Імпорт чи видалення локального профілю в **Settings** також миттєво оновлює пресети Slice-діалогу.

Сумісність визначається власним списком `compatible_printers` профілю (якщо є), потім за конвенцією іменування `@<принтер>` — в усіх трьох формах, які пише слайсер: `@BBL <model>`, повна `@Bambu Lab <model> <size> nozzle` (яку отримує збережений користувачем пресет) і голий тег `@<size>`. Голий розмір може *виключити* принтер, але ніколи не вважається доказом збігу, а розміри порівнюються числово, тож `0.20` і `0.2` — одне й те саме. Профілі Orca Cloud несуть власний список сумісних принтерів, а копія профілю, яка знає свої принтери, ділиться цим списком із копіями, що не знають — саме це не дає профілю, чия назва не містить моделі (`Overture PLA Matte @0.2`), бути автоматично обраним для принтера, під який його ніколи не робили. Вбудовані (standard) профілі теж несуть власний список сумісних принтерів слайсера, якщо сайдкар достатньо свіжий, щоб його віддавати, — саме це дає процеси P1S, X1, X1E чи H2D Pro, бо слайсер не постачає жодного, названого на їхню честь. Фільтр за принтером, що лишив би dropdown порожнім, показує натомість увесь список, і поле про це каже: *Невідомо, чи підходить цьому принтеру хоч один профіль, тож показано всі.* Вона **враховує сопло**, тож process під сопло 0.6 не буде сумісним для принтера із соплом 0.4 (0.4 — неявне за замовчуванням, що не несе суфікса). Той самий matcher керує підбором профілів у майстрі **калібрування філаменту**; там несумісні профілі ховаються повністю, а не групуються, бо калібрувальний друк на не тому принтері просто марнує стіл, а сторінка, що друкує, вимагає від профілю принтера більше, ніж збіг, — див. [Вибір слайсера, столу й пресетів](filament-calibration.md#choosing-presets).

**Slicer-picker** сидить угорі Slice-діалогу — дві картки-кнопки (дзеркалять "Filament Tracking"-патерн з Settings) з власними live-індикаторами здоров'я. Авто-локається на єдиний здоровий sidecar, коли інший лежить; ти вибираєш вільно, коли обидва доступні; offline-картки disabled. Перший раз default — глобальний *Preferred slicer*; наступні відкриття того самого source file пам'ятають твій останній вибір (per-file localStorage). Запам'ятовується лише вибір, який ти зробив на картці: слайсер, на який діалог переходить сам, поки один sidecar лежить, — ні.

Для multi-plate 3MF modal вбудовує **inline plate-selector** угорі body, дзеркаля picker плит з Print modal — вертикальний paginator + details-картка. Плита 1 авто-вибирається на load, щоб filament-requirements + presets-запити йшли без блокування на user-interaction; клік по іншій плиті пере-ключає ці запити. Чекбокс **Нарізати всі плити** над picker'ом: познач його, щоб нарізати всі плити в один multi-plate вихід (`plate=0`) замість однієї обраної.

**Перенарізання під інший принтер** — можна нарізати 3MF, зроблений під іншу модель. Обери будь-який профіль принтера, і слайсер перенаріже під цю ціль (стіл, кінематика, к-сть сопел і start-gcode беруться з обраного профілю). Коли ціль перетинає клас сопла (одне ↔ два сопла H2D/H2C/X2D), BamDude пробрасує `--arrange`, щоб BambuStudio переставив об'єкти під цільовий стіл і узгодив вбудовані налаштування; крос-клас «нарізати всі плити» нарізає кожну плиту окремо й зливає в один файл. Якщо слайсер усе одно не може дати валідний результат — його причина показується в діалозі, який треба закрити, а не в тості, що зникає.


### Списки профілів: групи, порядок і пошук { #preset-lists }

Кожен список профілів згруповано за **джерелом**, твої власні — першими:

1. **Імпортовані** — профілі, імпортовані в BamDude ([Local Profiles](local-profiles.md)).
2. **Orca Cloud** — твої профілі з [Orca Cloud](orca-cloud.md).
3. **Bambu Cloud — мої пресети** — пресети, які ти зберіг у своєму акаунті [Bambu Cloud](cloud-profiles.md).
4. **Bambu Cloud** — стокові пресети Bambu, як їх перелічує твій акаунт.
5. **Стандартні** — пресети, що йдуть разом зі слайсером у sidecar'і.

Порожня група не показується. У полі процесу чи філаменту профілі, зроблені для іншого принтера, ніж вибраний, ідуть у кінцевій групі **Інші принтери**, де кожен запис після назви називає своє джерело.

Назва — це не ідентичність. Стоковий пресет, який під однією назвою є і в Bambu Cloud, і в комплекті слайсера, — це **два записи**: один у групі **Bambu Cloud**, другий у **Стандартні**. Вміст у них різний — стандартний належить запущеному sidecar'у, — і жоден не підміняє іншого.

Усередині групи порядок такий: пресети Bambu, далі Generic, далі всі інші бренди; у списках філаменту матеріали підтримок (support, PVA, BVOH, HIPS) ідуть після всіх решти. Далі назви впорядковано без огляду на регістр, а числа — за значенням, тож `0.08mm` стоїть перед `0.20mm`, а `PA6` — перед `PA12`. Пресет, клонований у слайсері під типовою назвою `# …`, стоїть там, де стояв би пресет, який він копіює.

Сегмент **Джерело пресетів** над полями вибирає, чиї профілі показують списки: **Усі**, **Мої пресети** чи **Вбудовані**. Мої — це імпортовані, твої профілі з Orca Cloud і пресети, які ти зберіг у Bambu Cloud; вбудовані — стандартні пресети та стокові хмарні пресети Bambu. Уперше вибрано **Мої пресети**. Це одне налаштування для всіх місць, де сегмент є, — цього діалогу, [калібрування філаменту](filament-calibration.md) і [збирання проєкту](assemble-project.md), — і воно запам'ятовується в браузері. Зміна джерела наново робить автоматичні вибори процесу й філаменту; твої лишаються. Коли джерело ховає всі підхожі профілі поля, поле показує й вбудовані та каже про це: *Тут не підходить жоден ваш профіль, тож показано й вбудовані.* — з кнопкою **Показати всі**, яка ставить сегмент на **Усі**.

Кнопка з лупою біля списку відкриває поле пошуку (**Пошук пресетів…**). Набрані слова звужують цей список: кожне слово має траплятися в записі — у будь-якому порядку й регістрі. Вибраний пресет завжди лишається у списку. **Enter** бере перший збіг, **↓** переходить у звужений список, **Esc** закриває пошук, не закриваючи діалогу. Коли збігів немає, пошук каже **Нічого не знайдено.**

### Профіль, який обрав ти, лишається обраним { #explicit-choice }

Діалог робить автоматичні вибори — і замінює лише власні. Профіль процесу чи філаменту, який обираєш **ти** — зі списку або застосувавши [збережені налаштування](slicer-pipelines.md), — це явний вибір, і жоден автоматичний прохід його не замінює: ні **Оновити**, ні інша плита проєкту, ні **Нарізати всі плити**, ні зміна принтера, ні перевірка матеріалу, яка перевибирає автоматично підібраний філамент.

- **Обраний профіль, зроблений для іншого принтера, лишається.** Він стоїть у групі **Інші принтери**, а під полем про це сказано: *«Цей профіль призначено для іншого принтера, ніж вибраний.»* Автоматичні вибори йдуть за принтером; твої чекають на тебе.
- **Обраний профіль, якого більше немає у списках** — видалений чи зниклий після оновлення — замінюється автоматичним вибором, а банер називає поля, які варто перевірити: *«Вибраного вами профілю більше немає у списку, тому підставлено інший. Перевірте: …»*.
- **Профіль принтера, якого більше немає у списках, не замінюється**, хоч би хто його обрав. Поле каже *Вибраного профілю більше немає у списку. Щоб продовжити, виберіть інший.*, а **Нарізати** й збереження налаштувань чекають, доки ти не обереш профіль принтера, — навіть коли той самий профіль повертається після наступного **Оновити**.
- **Застосування збережених налаштувань** — єдина дія, крім твого власного вибору, що замінює вибір, і вона каже, що зробила: *«Застосовано «назва». Змінено: Профіль принтера, Профіль процесу»* — або *«Застосовано «назва». Нічого не змінилося — саме це вже було вибрано.»*

### Лише моделі моєї ферми, лише завантажені філаменти { #farm-filters }

Два перемикачі над полями профілів звужують списки до того, що ферма може надрукувати. Обидва типово вимкнені й запам'ятовуються в браузері.

| Перемикач | Звужує | До чого |
|---|---|---|
| **Лише моделі моєї ферми** | **Профіль принтера** | Профілі моделей принтерів твоєї ферми — кожного принтера, що не в архіві, у мережі він чи ні, на паузі чи на обслуговуванні, і моделей, файли яких Bambu Studio дозволяє цьому принтеру друкувати (P1S бере й профілі P1P та серії X1), — і з розміром сопла, встановленого на одному з них, коли профіль називає розмір. Принтер, чиї сопла невідомі, не виключає жодного розміру. |
| **Лише завантажені філаменти** | Кожне поле філаменту | Профілі філаментів, завантажених на принтерах у мережі. Щойно вибрано профіль принтера, рахуються лише принтери цієї моделі, що в мережі. |

- **У мережі**, для завантажених філаментів, — це підключений, активний і не архівований принтер.
- **Завантажений** — це котушка, призначена слоту: її власний профіль філаменту, а не те, що слот показує принтеру. Слот, оголошений принтеру як Generic-профіль для [AMS Backup](ams.md), рахується як філамент, що справді в ньому стоїть. Котушка без власного профілю філаменту зіставляється за матеріалом: рахується кожен профіль цього матеріалу. Зовнішні тримачі котушок рахуються; порожній слот — ні.
- **Списки йдуть за фермою, поки діалог відкритий**: принтер підключився чи відключився, котушку призначили чи зняли.
- **Фільтр звужує те, що пропонує список, і більше нічого.** Обраний тобою профіль лишається обраним і лишається у списку, навіть коли фільтр його сховав би, і фільтр ніколи не змінює профіль, обраний рукою. Автоматичні вибори йдуть за джерелом і за завантаженим філаментом: поле процесу чи філаменту, яке діалог заповнює сам, бере профіль, який ці фільтри пропонують, — обраного джерела й завантажений, поки ввімкнено **Лише завантажені філаменти**, — якщо він пасує матеріалу плити та принтеру, інакше — звичайний вибір. **Лише моделі моєї ферми** не змінює жодного вибору, а автоматичний вибір принтера не зважає на жоден фільтр.

Коли фільтр лишив би поле без жодного підхожого профілю, поле не лишається порожнім: воно саме відкладає цей фільтр, показує те, що лишилося, і називає відкладений фільтр — з кнопкою **Показати всі**, яка вимикає цей фільтр назовсім. Першим відкладається перемикач ферми, далі джерело:

| Поле | Повідомлення |
|---|---|
| Профіль принтера | *Тут не підходить жоден профіль моделі вашої ферми, тож показано всі профілі принтерів.* |
| Профілі філаменту | *Тут не підходить жоден профіль завантаженого філаменту, тож показано всі профілі філаментів.* |
| Будь-яке поле | *Тут не підходить жоден ваш профіль, тож показано й вбудовані.* |

Перемикачам потрібне право переглядати принтери (`printers:read`); без нього вони не показуються. Коли стан принтерів прочитати не вдається, нічого не звужується, і діалог про це каже — *«Не вдалося прочитати стан принтерів, тому показано всі профілі.»* — з кнопкою **Повторити**. На обидва перемикачі відповідає один запит, `GET /api/v1/slicer/loaded-filaments`; [API-ключ](api-keys.md), обмежений кількома принтерами, бачить лише їх.

### Тип столу { #bed-plate }

Поле **Тип столу** задає плиту, під яку робиться нарізка (`--curr-bed-type` на CLI):

| Плита | З яким слайсером |
|---|---|
| **Cool Plate** | обидва |
| **Engineering Plate** | обидва |
| **Smooth PEI / High Temp Plate** | обидва |
| **Textured PEI Plate** | обидва |
| **Cool Plate SuperTack** | обидва |
| **Textured Cool Plate** | лише OrcaSlicer |

Типова **Textured PEI Plate** відповідає заводській плиті на сучасній лінійці Bambu; власники A1 / A1-mini переключаються на SuperTack один раз, і обрана плита запам'ятовується в браузері. Нарізані 3MF із Bambu Studio все ще шанують свій вбудований per-plate `bed_type` (BamDude форвардить оригінальні байти) — override спрацьовує тільки для джерел без нього.

**Textured Cool Plate** є лише в OrcaSlicer, тож вона є у списку, поки слайсер цього завдання — OrcaSlicer. Коли слайсер — Bambu Studio, а поточна плита саме ця, діалог змінює її на типову й каже про це під полем — *«Textured Cool Plate є лише в OrcaSlicer. Тип столу змінено на Textured PEI Plate.»* — а повернення до OrcaSlicer повертає її назад. Запит на нарізку, що називає її для Bambu Studio, відхиляється (422): *«Textured Cool Plate є лише в OrcaSlicer. Виберіть інший стіл або нарізайте в OrcaSlicer.»*

Той самий вибір, з тим самим запам'ятованим столом, є на обох сторінках [калібрування філаменту](filament-calibration.md#choosing-presets), і запит калібрування, що називає Textured Cool Plate для Bambu Studio, відхиляється так само.

### Пресети, які пропонує слайсер { #standard-presets }

Група **Стандартні** — це набір пресетів слайсера всередині sidecar'а:

- **Пресети, які бренд тримає у власній теці** (P1P, Polymaker, SUNLU та інші), перелічені разом з рештою.
- **Пресет із `/` у назві** (`Bambu Support For PLA/PETG …`) стоїть у списку під цією назвою і нарізається з власними налаштуваннями.
- **Бібліотека філаментів OrcaSlicer** — пресети з назвою `… @System` — пропонується з OrcaSlicer; у Bambu Studio такої бібліотеки немає. Бібліотечний пресет, який називає свої принтери (`Polymaker PolyLite PLA @BBL A1`), пропонується для цих принтерів. Загальний (`Generic PLA @System`) пропонується для принтера лише тоді, коли той **не має власного пресета для того самого філаменту** — «той самий філамент» означає назву до знака `@`, — тож принтеру з `Generic PLA @BBL X1C` поруч не пропонується `Generic PLA @System`.
- **Профіль принтера, збережений під власною назвою** (`Bambu Lab H2D 0.4 nozzle - Skew`), — це той принтер, з якого його збережено: модель, сопло й сумісні профілі процесу та філаменту в нього батьківські, і нарізається він як цей принтер із твоїми змінами. Профіль принтера, клонований у слайсері під типовою назвою `# …`, зіставляється як пресет, який він копіює.

### Нарізати як задумано (зберегти вбудовані налаштування файлу)

Зазвичай нарізання застосовує обрані тобою пресети **Принтер / Процес /
Філамент**, які *перекривають* усе, що автор файлу вклав у вбудований
`project_settings.config`. Саме це перекриття дозволяє перенарізати під інший
принтер — але через нього модель із [MakerWorld](makerworld.md), налаштована,
скажімо, на п'ять стінок, виходить із двома за замовчуванням твого пресета.

Коли вихідний 3MF несе вбудовані налаштування **і** обраний тобою принтер
збігається з тим, під який файл проєктували, у модалці з'являється чекбокс
**Використати вбудовані налаштування файлу**. Постав його — і BamDude нарізає без
перекриття пресетами, тож результат визначають авторські кількість стінок,
заповнення, філамент та інші налаштування процесу.

- **Дропдауни пресетів і вибір типу столу блокуються** — принтер, процес,
  філамент і тип столу. На цьому шляху вони не використовуються, тож блокуються,
  щоб це було очевидно (і щоб зміна принтера не витягла тебе непомітно з дизайну,
  сховавши чекбокс).
- **Філамент теж береться з файлу**, а не з твоїх виборів AMS. Якщо філаменти
  файлу не збігаються із зарядженим — зістав їх на принтері або зніми чекбокс і
  обери свої.
- **Пропонується лише коли твій принтер збігається з цільовою моделлю дизайну.**
  Дотримання вбудованих налаштувань для *іншої* моделі поставило б об'єкт на
  неправильний стіл — саме для цього існує шлях із пресетами — тож чекбокс просто
  не показується, коли принтер інший.

!!! note "Це не злиття налаштувань"
    Або-або: ти отримуєш повний профіль дизайнера, або свій. Залишити авторські
    стінки, підмінивши *свій* філамент, тут не вийде — для цього є **Налаштування
    друку дизайнера** нижче: там вибір по кожному параметру, і воно працює між
    різними принтерами.

### Налаштування друку дизайнера (по параметрах, між принтерами)

Середина між «твій пресет» і «нарізати як задумано»: обираєш власні принтер,
процес і філаменти — і переносиш **лише окремі параметри, які змінив автор**.

Коли вихідний 3MF декларує відхилення від свого стокового профілю, діалог Slice
додає панель **The designer's print settings** зі списком саме тих параметрів
процесу, які змінив автор, і того, у що кожен виставлений, — з чекбоксом на
кожен. Застосовується тільки те, що ти позначив.

| Група | Приклади | Типово |
|---|---|:---:|
| **Задум дизайну** | кількість стінок, щільність і патерн заповнення, підтримки, шов, брим, ironing | :material-check: позначено |
| **Визначає пресет** — бейдж `перебиває пресет` | висота шару, висота першого шару | :material-close: не позначено |
| **Підлаштоване під машину** — бейдж `machine-tuned` | швидкості, прискорення, ривок, обдув, температури, геометрія prime tower | :material-close: не позначено |

Висота шару й першого шару — це *і є* вибраний пресет процесу («0.08mm High Quality» — його висота
шару), тож значення з файлу пропонується поряд зі значенням пресету, але ніколи не позначається за тебе:
0.2 з файлу ніколи не нарізається тихо поверх явно вибраного пресету 0.08.

Підлаштовані під машину значення автор обирав для *свого* принтера. На твоєму
вони можуть бути просто хибними — або поза діапазоном, який приймає твій профіль,
що завалює нарізку взагалі. Тому вони показані з бейджем і лишені вимкненими, щоб
вирішував ти.

**Підтримки слідують за галочками.** Файл із увімкненими підтримками вмикає їх
і для твоєї нарізки — це задум дизайну, позначений за замовчуванням. Зніми
галочки — і нарізка лишить налаштування підтримок твого пресету; знятий параметр
підтримок не переноситься потай. Файл, що не записує жодних відхилень
(скажімо, експорт з OrcaSlicer), не має чого позначати, і його підтримки
переносяться як є.

Ті самі галочки є біля кожного параметра в панелі **Process settings**, і галочка
в будь-якому з двох місць — це одна галочка. Панель сірить параметр лише тоді,
коли його вимкне сама нарізка — за значеннями твого пресету, позначеними
значеннями з файлу і тим, що ти ввів, а не за вбудованими дефолтами слайсера,
через які сіріла б уся сторінка Support для пресету з увімкненими
підтримками. Галочку «з файлу» на сірому параметрі все одно можна зняти.

!!! info "Тут нічого не вгадується"
    Bambu Studio сам записує перелік відхилень у файл
    (`different_settings_to_system` у `Metadata/project_settings.config`).
    BamDude читає цей перелік, а не порівнює профілі й не здогадується про намір.

    Файл, чий перелік не збігається з його ж кількістю слотів філаменту,
    **ігнорується, а не інтерпретується**: хибне прочитання ризикує перенести
    стартовий G-code машини автора на твій принтер.

Панель працює й при нарізці для **іншого** принтера — саме там, де «нарізати як
задумано» не пропонується. Вона так само з'являється при передруку з архіву.

### Слоти філаменту, які твоя плита не використовує

У мультиплейтовому проєкті кожна плита зазвичай малює лише частиною слотів
філаменту проєкту. Діалог нарізання підписує решту **«— не використовується цією
плитою»** і глушить їхні дропдауни — але слайсер усе одно хоче профіль для
кожного слота й перевіряє їх усі.

Тому перед нарізанням однієї плити BamDude замінює профіль кожного невикористаного
слота профілем із **найменшого використаного слота** плити — лише профіль: власний колір слота в нарізаному файлі лишається. Це зберігає кількість
слотів (і посилання файлу на них), водночас роблячи заряджений набір і однорідним
за матеріалом, і прив'язаним до цільового принтера — тож жоден валідатор не
спрацює на слоті, якого G-code навіть не торкається:

- *«the temperature difference of the filaments used is too large»* — дефолтний
  ABS поруч із PLA, яким плита насправді друкує.
- *«filament preset (slot N) is not compatible with printer …»* — профіль,
  збережений для іншого принтера (напр. філамент `@Bambu Lab H2D`, вшитий у
  вихідний файл), у слоті, який твоя плита ігнорує.

Нарізання **всіх плит** цього не робить: у межах усього проєкту кожен визначений
слот кимось використовується, тож профіль кожного шанується як обрано.

### Розфарбовані багатоколірні моделі { #painted-models }

Модель, розфарбована в слайсері кількома філаментами, зберігає свої кольори після нарізки тут. Якими слотами друкує плита, читається і з призначень філаменту об'єктам, **і** з даних розфарбування на їхніх поверхнях, і рахується кожна зафарбована ділянка, хоч яка мала: колір, ужитий на одній дрібній деталі, робить свій слот використаним, і той нарізається з обраним для нього профілем. Слот, якого плита справді не використовує, зберігає в нарізаному файлі власний колір, хоч який профіль його заміщає.

### Індикатори доступності

Здоров'я sidecar'ів виходить на трьох поверхнях, всі шерять один React-Query-кеш + ендпоінт `GET /api/v1/slicer/health/{slicer}` (30 с in-process cache):

- **Settings → Profiles → Slicer API** — невеликий inline-статус біля кожного URL-поля (зелений чек + версія, або червоний хрестик з помилкою).
- **Slice modal** — кожна картка picker'а несе live-індикатор здоров'я (див. вище), а під картками є примітка, коли контейнер вибраного слайсера старіший, ніж потрібно BamDude, — див. [Оновлення sidecar'ів](#updating-the-sidecars).
- Секція **Інформація → Slicer-sidecar'и** — версія + доступність + URL кожного sidecar (auto-refresh 30 с разом із рештою system info).

Persistent-toast у нижньому правому кутку трекає job: live progress percent + elapsed time, заміняється transient success/error toast при завершенні. Sliced-output лягає в ту ж папку бібліотеки як `.gcode.3mf` з `source_type='sliced'` provenance — оригінал не чіпається.

## :material-shield-key: Дозволи

| Permission | Що дозволяє |
|------------|--------------|
| `library:upload` | Тригерити слайсинг із File Manager (sliced-output — це свіжий library-upload). |
| `archives:reprint_own` / `archives:reprint_all` | Нарізати архів — поруч із `library:upload`. Повторна нарізка створює з архіву нову роботу для друку, тож питає право його передруковувати: власні друки або будь-які. API-ключ не може перенарізати архів, якого його власник не бачить. |

| `cloud:auth` | Потрібно щоб тягнути `cloud` preset-tier — без неї modal показує тільки `local` + `standard` tier'и. |
| `printers:read` | Перемикачі **Лише моделі моєї ферми** / **Лише завантажені філаменти** в діалозі нарізки — без цього права вони не показуються. |

Settings → Profiles → Slicer API toggle і URL-поля гейтяться `settings:update`.

## :material-alert-circle-outline: Режими провалу { #failure-modes }

- **Sidecar offline** → 502 у toast'і, job marked failed; оригінал не чіпається. «Не вдалося під'єднатися» і «перестав чекати» — це **різні** повідомлення, і в повідомленні про таймаут названо, який ліміт вичерпано і де його змінити.
- **Нарізка не дала результату** → відповідь, яка є «OK» на кілька байтів — зламана конфігурація slicer-сервісу, reverse proxy, що повернув власну сторінку помилки, обрізана відповідь, падіння слайсера без запису виводу — **відхиляється до збереження файлу**, а не зберігається, ставиться в чергу й вирушає на принтер, який потім нічого не робить. Нарізку, відхилену як завелику, названо тим, чим вона є: обмеженням розміру на проксі перед слайсером, а не збоєм слайсера.
- **Profile not found** → 400 називає відсутній профіль — додай через [K-Profiles](kprofiles.md) або обери інший tier.
- **Пресет, який слайсер не може розв'язати** → пресет — це ланцюжок: він успадковує від батьківського, і слайсер має знайти кожну ланку. Коли якоїсь бракує, нарізка відхиляється і нічого не нарізається — ніколи на вбудованих типових значеннях слайсера, — а повідомлення називає пресет і відсутній батьківський профіль: *«Профіль «X» не можна нарізати: його батьківського профілю «Y» немає серед профілів слайсера, тому нічого не нарізано. Виберіть інший профіль або перезберіть контейнери слайсера, якщо батьківський профіль належить новішій версії слайсера.»* Для вибору зі **Стандартних**, якого запущений слайсер не має: *«Профілю «X» немає серед профілів слайсера, тому нічого не нарізано. …»* Що робити: обрати інший пресет — стоковий для того самого принтера чи філаменту; імпортований пресет, батьківський профіль якого не завантажився під час імпорту, імпортувати заново, коли батьківський стане доступним ([Local Profiles](local-profiles.md)); якщо батьківський профіль належить новішому слайсеру — підняти версію слайсера і [перезібрати контейнери](#updating-the-sidecars). Ця відмова не переходить на вбудовані налаштування файлу (нижче) і потребує актуального sidecar'а.
- **Sidecar відмовив файл** (corrupt 3MF, unsupported plate, malformed preset, etc.) → toast показує дослівний CLI stdout/stderr sidecar'а — не треба копати в логах контейнера.
- **Автоматичний повтор із вбудованими налаштуваннями** — після збою слайсера з вибраними профілями BamDude може один раз повторити нарізання 3MF із налаштуваннями в `Metadata/project_settings.config`. Повтор можливий, якщо у файлі й вибраному профілі визначено ту саму відому модель принтера. Інакше показується початкова помилка. Успішний повтор позначається як `used_embedded_settings: true`.
- **Cloud presets unreachable** (token expired / network down) → modal рендерить `cloud`-tier зі status-banner'ом і фолится на `local` + `standard` only.
