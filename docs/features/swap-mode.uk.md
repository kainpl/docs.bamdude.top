# Swap Mode

Swap mode підтримує автоматизовані плейт-свопери -- механічні додатки, що виштовхують готову робочу пластину та позиціонують свіжу між друками. Коли swap mode увімкнено, BamDude координується зі свопером, щоб виконувати unattended-батчі без ручного підтвердження очищення пластини.

---

## :material-swap-horizontal: Що таке Swap Mode?

Плейт-свопер -- це апаратний аксесуар (найчастіше для A1 Mini), що бере на себе ротацію пластин між друками. Зі swap mode увімкненим планувальник черги:

1. Виконує макрос **`swap_mode_start`** перед першим друком
2. Запускає сам друк
3. Виконує макрос **`swap_mode_change_table`** після завершення друку
4. Обходить підтвердження plate-clear
5. Автоматично запускає наступний друк з черги

Цикл триває, поки черга не спорожніє.

## :material-cog: Налаштування

### Увімкнення Swap Mode

1. Перейдіть до **Settings → Queue**.
2. Увімкніть **Swap Mode** для свого A1 Mini.
3. Виберіть **Swap Profile** під своє залізо:

    | Профіль | Для |
    |---|---|
    | `a1mini_kit` | Офіційний Bambu A1 Mini Plate Swapper Kit |
    | `a1mini_stl` | Community-printable A1 Mini свопери (printable kit / STL дизайни) |
    | `jobox-a1` | JoBox plate-swap автоматика |

    Профіль прив'язує правильний набір макросів `swap_mode_start` / `swap_mode_change_table`. **`a1mini_stl` і `jobox-a1` постачаються з seed-нутими built-in-макросами**; **`a1mini_kit` — ні** (офіційний кіт Bambu наразі покладається на user-supplied G-code — напишіть власну пару під **Settings → Macros** і позначте `swap_profile=a1mini_kit`). Built-in-и будь-якого профілю можна перевизначити, відредагувавши макрос у UI.

### Swap G-code макроси

Swap mode керується G-code макросами, прив'язаними до подій `swap_mode_start` та `swap_mode_change_table`. Налаштовуйте їх у **Settings → Macros**. Див. [Макроси](macros.md) для повної системи подій + фільтрів.

```gcode
; Приклад сніпета swap_mode_change_table
G28 X Y         ; Home X and Y
G1 Y 180 F3000  ; Move bed forward for plate swap
M400            ; Wait for moves to complete
G4 S5           ; Pause 5 seconds for swap
G28             ; Home all axes
```

!!! warning "Потрібне власне обладнання"
    Swap mode потребує фізичного плейт-свопера, прикрученого до принтера.
    Підлаштовуйте G-code `swap_mode_change_table` під ваш конкретний
    механізм -- універсальної swap-рутини не існує.

## :material-shield-check: Restart-стійке відстеження подій

Swap-намір **зберігається на диск**, а не в пам'яті. Рестарт BamDude посеред друку ніколи не втрачає очікуваний plate-swap.

**Як це працює**

- На диспатчі кожна swap-подія, яку завдання збирається виконати, додається в `print_archives.extra_data["swap_macro_events_pending"]` (JSON-список).
- Коли `swap_mode_start` спрацьовує успішно, диспатчер одразу видаляє його зі списку.
- Коли `swap_mode_change_table` спрацьовує успішно (в `on_print_complete`), той самий запис видаляє його.
- Щойно список порожніє, ключ зникає взагалі, тож `extra_data` архіву залишається чистим.
- `swap_mode_change_table`, який не може виконатися наприкінці друку (утримана заміна, див. нижче), лишається
  у списку як запис того, що не зроблено, — сам по собі пізніше він ніколи не виконається.

**Чому це важливо**

- Рестарт бекенду між print start та print complete раніше витирав in-memory dict `_active_swap_config`, лишаючи `on_print_complete` без нічого, на чому діяти. Тепер pending-список читається з рядка архіву, і спрацьовують лише ті події, що в ньому ще лишилися.
- Дубльований `on_print_complete` (MQTT replay, reconnect flap) знаходить подію вже видаленою і нічого не робить -- жодного подвійного swap.

!!! info "Де живе маркер"
    Для диспатчів файлів бібліотеки початковий pending-список загортається
    в `INSERT` всередині `archive_print()` (один statement, без додаткового
    writer). Для повторних друків існуючий рядок архіву оновлюється у
    відкритій сесії диспатчера до FTP-завантаження -- тримання всього в
    одній транзакції уникає гонки з runtime-трекером по тому ж рядку.

## :material-lock-clock: Диспатч і startup-lock на DB-write

Background dispatch працює **паралельно по принтерах** — відправка друків на два A1 Mini зі сваперами справді стартує обидва завдання одночасно.

**Що серіалізовано**

Коротка фаза DB-insert (`INSERT INTO print_archives`) обгорнута в startup-lock, щоб single-writer семантика SQLite не падала на `database is locked`. Лок звільняється, як тільки рядок закомічений; FTP-завантаження і `start_print` MQTT round-trip далі біжать паралельно.

**Що ти побачиш**

- На двох принтерах `swap_mode_start` спрацьовує практично одночасно.
- Їхні FTP-завантаження йдуть паралельно (у dispatch-тості будуть два прогрес-бари).
- Тимчасовий "одне за раз через усю ферму" gate, що приземлився в середині 0.4.1, прибрали, як тільки startup-lock у диспатчер заїхав.

## :material-playlist-play: Поведінка черги в Swap Mode

Коли swap mode активний для принтера:

1. Друк завершується на принтері.
2. Виконується макрос `swap_mode_change_table` (G-code через MQTT, з ACK у idle-стані) — для друку, який
   BamDude може довести як свій, над файлом, про який відомо, що він не декларує власної послідовності (див.
   [Утримана заміна столу](#утримана-заміна-столу)).
3. **Підтвердження plate-clear обходиться** -- свопер сам розбирається з очищенням.
4. Наступний друк з черги диспатчиться.
5. Цикл повторюється, поки черга не спорожніє.

Це режим **unattended batch production** для сумісних принтерів.

!!! warning "Запускайте друк з BamDude, а не з екрана принтера"

    Swap-макроси виконуються лише для друків, які **запустив BamDude** -- з
    черги, з Auto-Queue, передруком з архіву або через Send-to-Printer. Друк,
    який ви запустили на самому екрані принтера (чи зі слайсера напряму в
    машину), не проходить через диспетчер BamDude, тому:

    - макрос `swap_mode_change_table` **не виконується** -- стіл не міняється, і
      готова деталь лишається на місці;
    - оскільки плиту ніхто не звільнив, BamDude перед наступним друком з черги
      попросить вручну натиснути **Очистити стіл** -- так само, як для принтера
      без swap-режиму.

    Виглядає це так, ніби принтер вільний, а черга не рухається. Натисніть
    **Очистити стіл** на карточці принтера, коли стіл справді порожній, і черга
    поїде далі.

    Єдиний виняток -- файл, який **декларує власну послідовність заміни столу**
    (саме такі експортує swaplist.app -- див. розділ про власну послідовність нижче):
    зміна столу зашита в його G-code, тож він міняє стіл коректно навіть при запуску
    з принтера. Коли BamDude бачив цей запуск і завантажив файл, підтвердження не
    питається; друк, який він знайшов лише за назвою пізніше, все одно питає.

!!! note "Скасований або невдалий друк завжди просить підтвердження"

    Swap-макроси свідомо пропускаються, коли друк завершився не успішно: деталь
    (або те, що від неї лишилось) досі на столі, і заміна столу в такому стані
    або заклинить механізм, або заведе забруднену плиту під наступний друк. Саме
    тому черга після збою зупиняється й чекає на вас -- це безпечна поведінка, а
    не поломка.

    Якщо друк позначено невдалим через те, що BamDude **втратив звʼязок із
    принтером під час swap-макросу**, у повідомленні це сказано прямо -- це
    проблема мережі, а не макросу. Короткі обриви перечікуються 30 секунд, і лише
    потім друк вважається провальним.

## :material-file-check: Власна послідовність заміни столу у файлі

Деякі файли несуть заміну столу **всередині свого G-code** — саме такі експортує swaplist.app. BamDude не повинен
додавати до них свої swap-макроси, інакше стіл заміниться двічі. Чи несе файл таку послідовність — це **декларація**,
яку файл робить один раз, і друк її зберігає.

**Як файл її декларує.** Власною назвою, коли він уперше потрапляє в BamDude — завантаження, елемент ZIP (назва
елемента, не самого ZIP), скан зовнішньої теки, Virtual Printer, імпорт з MakerWorld, файл, збережений з принтера:
маркер `.swap.` або `.swaps.` **між крапками** (`Tray.swaps.gcode.3mf`). Пізніше перейменування нічого не декларує;
скан зовнішньої теки читає назву знову лише тоді, коли змінився вміст файла. Файли, які BamDude нарізає сам, власної
послідовності не декларують.

**Друк її зберігає.** Поставлене в чергу завдання захоплює декларацію разом із байтами файла: перейменування файла в
бібліотеці, копія завдання чи видалення оригіналу нічого не змінюють, а архів друку її записує, тож і передрук її
несе.

| Файл… | Swap-макроси BamDude | Список принтерів |
|---|---|---|
| декларує власну послідовність | не додаються | лише принтери у swap-режимі |
| не декларує | ті swap-макроси, які ви обрали | усі принтери |
| **невідомий** | не вгадуються — див. нижче | усі принтери |

**Що невідомо.** Друк, заархівований до того, як це почали записувати (BamDude цього не зберігав, тож старому «ні»
не довіряє); файл бібліотеки без хешу вмісту — у зовнішній теці доки скан теки його справді не прочитає, керований —
доки його не завантажать знову як нову копію, — і тег SWAP тим часом не показується; друк, запущений з екрана
принтера, чий файл не вдалося завантажити. Будь-яке з них можна [задекларувати самому](#задекларувати-файл-самому).

**Старіші зовнішні файли.** Файл, який скан зовнішньої теки приніс до цієї версії, мав записане лише «ні», що б він
не містив. Тепер BamDude судить такий файл за його іменем **на спільному ресурсі** — за тим самим правилом `.swap.` /
`.swaps.`, що й новий файл, — ніколи не за іменем, яке показує бібліотека і яке змінює перейменування в BamDude.
Оновлення записує цю відповідь один раз, тож тег SWAP і фільтр за тегом з нею узгоджені. Керований файл бібліотеки з
давніших часів зберігає свою відповідь: BamDude вже не може сказати, чи те «ні» було декларацією, чи старим
типовим значенням. Ім'я на диску може помилятися щодо того, що робить G-code, — це та сама довіра, що й до імені
нового файлу; якщо є сумнів, задекларуйте файл самі.

**Над невідомим джерелом** запит swap-макросів BamDude відхиляється, а не вгадується:

- діалог друку каже, що swap-сумісність джерела невідома, і пропонує **Друкувати без додаткових swap-макросів** для
  цього одного завдання — збережені налаштування swap і те, що груповий запуск передає наступному файлу, лишаються
  без змін. Без наших макросів діють звичайні правила столу принтера: з увімкненим підтвердженням очищення столу
  наступна робота чекає, доки стіл очистять;
- завдання, яке вже стояло в черзі з нашими swap-макросами, завершується помилкою ще до надсилання й каже чому.
  **Повторити** надсилає його знову точно таким самим, тож воно знову не пройде; поставте файл у чергу заново з
  вимкненими swap-макросами або передрукуйте архів з **Друкувати без додаткових swap-макросів**;
- завдання AutoQueue чекає на принтер без swap-режиму, якщо такий міг би його надрукувати, зайнятий він чи ні, і
  завершується так само помилкою лише тоді, коли такого немає.

**Збереження архіву в бібліотеку** переносить його відому декларацію — і вашу теж, див. нижче. Невідому — відхиляє,
як і файл, що вже є в бібліотеці з протилежною декларацією; сам архів лишається.

### :material-account-check: Задекларувати файл самому

Коли ім'я нічого не каже або каже неправильно, скажіть самі: **Декларація swap-сумісності…** в меню архіву й у меню
файлу 3MF чи G-code у бібліотеці або **Задекларувати це джерело…** у примітці про невідоме джерело в діалозі друку. Потрібне право
редагувати цей архів чи файл.

1. BamDude **читає файл**, який надрукував би повторний друк, і показує його ім'я, розмір, хеш вмісту і поточну
   декларацію.
2. Ви обираєте **Файл уже містить власну послідовність зміни столу** або **Файл не містить власної послідовності
   зміни столу** — нічого не вибрано за вас. Це ваше твердження про файл, а не аналіз його G-code: «не містить»
   дозволяє запитані роботою swap-макроси; «містить власну» означає, що BamDude не додає жодного свого
   swap-макросу. Збережені налаштування swap не змінюються.
3. **Зберегти декларацію** читає файл ще раз і зберігає декларацію лише для **саме тих байтів, які ви бачили**. Якщо
   файл тим часом змінився або хтось задекларував його першим, нічого не збережено — прочитайте його знову й
   вирішіть знову. Хто й коли задекларував, зберігається разом із декларацією, і діалог показує це щоразу, коли
   ви його відкриваєте; декларацію, відновлену з резервної копії, позначено окремо.

Для архіву це декларація його **файлу** для майбутніх повторних друків. З чим виконувався заархівований друк — і все,
що лишилося за ним до сплати наприкінці, як-от утримана заміна столу, — лишається точно таким, як записано.

**Роботи, що вже в черзі, зберігають власну відповідь.** Робота захопила декларацію разом зі своїми байтами, коли її
поставили в чергу, тож нова декларація сама до неї не доходить. Після збереження — або коли ви відкриваєте діалог для
файлу, що вже має вашу декларацію, — він показує роботи, що очікують
або завершилися збоєм і друкують цей файл, і дає **застосувати** декларацію до вибраних — жодної не вибрано за вас.
Отримати її може лише робота, чия власна відповідь невідома, яка містить саме ці байти і яку ще ніколи не надсилали
на принтер; роботу з власною відповіддю ніколи не перезаписує (поставте файл у чергу знову, щоб друкувати з новою).
Вибрані роботи змінюються разом або жодна. Якщо хтось задекларує файл інакше, поки діалог відкритий, список
зникне, і діалог попросить прочитати файл знову: нічого не застосовується за декларацією, якої вам не показали.
Застосування — не повтор: робота зі збоєм лишається зі збоєм, доки ви не
натиснете **Повторити**.

### :material-pause-circle: Утримана заміна столу

Коли друк закінчується, BamDude виконує власний `swap_mode_change_table` лише для друку, який він може довести як
свій (власна диспетчеризація, запуск з екрана принтера, який він бачив, або точний id завдання принтера), що
**завершився успішно**, на принтері, який досі у swap-режимі й має макрос зміни столу, і лише над файлом, про який
відомо, що він **не** декларує власної послідовності. Інакше — невідомий або самозмінний файл, завершення, яке не
вдається пов'язати з друком, невдалий чи скасований друк, вимкнений swap-режим, відсутній макрос, результат,
непевний після перерви, —:

- нічого не надсилається, а крок лишається належним — сам по собі пізніше він ніколи не виконається;
- стіл не вважається очищеним;
- черга принтера **ставиться на паузу**, навіть коли підтвердження очищення столу вимкнене, з причиною на завданні,
  яке друкувалося, на наступному в черзі й бейджем **Swap утримано** на друку в архіві. Причина каже, чи зміна столу
  **розпочалася**, **могла розпочатися** чи не починалася.

BamDude надсилає макрос зміни столу щонайбільше один раз на друк. Два одночасні перепідключення, перезапуск
посеред нього чи помилка під час виконання утримують чергу так само, а не надсилають його вдруге; друк, чий принтер
уже зайняло інше завдання, не чіпає черги того завдання; а якщо BamDude зупинився, завершуючи зміну столу, наступне
підключення до принтера доводить її облік до кінця або утримує чергу.

Огляньте механізм заміни й стіл, очистіть стіл, якщо треба, і відновіть чергу як завжди. Успішно завершене завдання,
яке друкувалося, лишається в черзі зі своєю причиною: з увімкненим підтвердженням очищення столу його прибирає підтвердження, з
вимкненим — приберіть його самі. Так само файл із власною
послідовністю звільняє стіл лише для такого доведеного, успішного друку — ніколи для друку, який BamDude знайшов лише
за назвою, і ніколи для замовлення з автоскиданням, яке має власну обробку столу.

## :material-lightbulb-on: Парування з макросами `print_started` / `print_finished`

Новіші події `print_started` та `print_finished` (див. [Макроси](macros.md)) спрацьовують *додатково до* swap-макросів, на кожному друку незалежно від swap mode. Використовуйте їх для ортогональної автоматизації -- світло корпусу, зовнішні реле тощо.

**Приклад: світло корпусу тільки на swap-mode друках**

| Macro 1 | Macro 2 |
|---------|---------|
| Action: MQTT-action | Action: MQTT-action |
| Event: `print_started` | Event: `print_finished` |
| Command: `chamber_light_on` | Command: `chamber_light_off` |
| `swap_mode_only`: `true` | `swap_mode_only`: `true` |
| `delay_seconds`: `10` | `delay_seconds`: `0` |

Світло цикл лише на справжніх swap-mode прогонах; ручні друки з того ж принтера лишають світло недоторканим.

## :material-lightbulb: Поради

!!! tip "Перевірте swap-макрос вручну"
    Запустіть G-code `swap_mode_change_table` з файлового браузера принтера
    (або через **Macros → Run Now**) перш ніж вмикати swap mode у
    проді. Поганий swap-роутин заклинює всю чергу.

!!! tip "Поєднуйте з batch quantity"
    Використовуйте функцію batch-quantity у черзі, щоб поставити N копій,
    а далі дайте swap mode прогнати їх підряд. Поєднайте з авто-вимкненням
    розумних розеток для повністю unattended нічних прогонів.

!!! tip "Моніторте дистанційно"
    Стрім із камери + Telegram-бот дозволяють спостерігати за swap-операцією
    та отримувати сповіщення про завершення черги або збій. Див.
    [Telegram-бот](telegram-bot.md) і [Камеру](camera.md).

> Початково базується на документації [Bambuddy](https://github.com/maziggy/bambuddy).
