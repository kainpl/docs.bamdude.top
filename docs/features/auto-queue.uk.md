# Авто-черга (Auto-Queue Routing)

Авто-черга — це **шар-маршрутизатор поверх черг окремих принтерів**. Кидаєш у неї друк без вказівки конкретного принтера — планувальник сам обирає придатний вільний принтер (за моделлю + типом і кольором філаменту), копіює елемент у чергу того принтера, а далі вже відпрацьовує звична per-printer диспетчеризація.

Зʼявилася в **0.4.2**.

---

## :material-router-network: Як це працює

```
┌────────────────┐   є придатний вільний принтер?
│ AutoQueueItem  │────────┐
│ (target_model, │        │ так → копіюється в print_queue принтера
│  filaments,    │        │       auto-рядок стає "assigned"
│  colors)       │        │
└────────────────┘        ▼
                     PrintScheduler підхоплює його
                     протягом ~1 тіку (background_dispatch)
```

Фоновий цикл (`AutoQueueScheduler`, стартує з `main.py` lifespan) прокидається кожні **30 секунд** і на кожному тіку:

1. **Знімає список зайнятих принтерів** — усе що зараз `status='printing'` в `print_queue` виключається з цього раунду.
2. **Читає pending авто-чергові рядки** в порядку SJF (Shortest Job First) + `been_jumped`, якщо ввімкнено налаштування **Queue Shortest First**, інакше — за `position`.
3. **Для кожного елемента викликає `find_eligible_printer`** — шукає придатний принтер що відповідає:
    - `target_model` елемента (наприклад `X1C`, `P1S`, `A1MINI`, `H2D`)
    - усім `required_filament_types` (витягнуті з 3MF, користувач може перевизначити)
    - вимогам по кольору (коли `force_color_match=true`)
    - опційному `target_location` (тег кімната/стелаж), якщо ти групуєш принтери за локацією.
4. **Якщо є збіг** — елемент копіюється в `print_queue` цього принтера з AMS-мапінгом, обчисленим зі поточного стану котушок принтера. Auto-рядок переходить у `status='assigned'` і отримує посилання на створений per-printer елемент.
5. **Якщо збігу немає** — оновлюється `waiting_reason`, щоб черговий UI міг пояснити, *чому* елемент стоїть (наприклад `"всі P1S зайняті"`, `"треба PETG (червоний), у жодному принтері не заряджений"`).

Щойно рядок осідає в per-printer черзі — спрацьовує **звичний потік диспетчеризації**: гейт plate-clear, staggered start, swap-макроси, сушка, усе як завжди. Маршрутизатор нічого не оминає.

## :material-sort-numeric-ascending: SJF + захист від голодування

Коли увімкнено **Queue Shortest First** (Налаштування → Друк → Queue & Scheduling → Auto-Queue Routing → Queue Shortest First), pending-рядки сортуються:

```
ORDER BY been_jumped DESC,
         estimated_print_time_seconds ASC,
         position ASC
```

Sticky-біт `been_jumped` запобігає голодуванню: щоразу як SJF проштовхує коротший друк *повз* довший, довший отримує `been_jumped=True` і випливає на верх наступного раунду незалежно від часу друку. Так 14-годинний друк не стоятиме безкінечно за потоком 30-хвилинних завдань.

Якщо тогл вимкнено — елементи диспатчаться в порядку FIFO (за `position`).

## :material-cog: Налаштування

**Налаштування → Друк → Queue & Scheduling → Auto-Queue Routing**:

| Налаштування | Що робить |
|--------------|-----------|
| **Queue Shortest First** | Вмикає SJF + захист від голодування. За замовчуванням: вимкнено (FIFO). |

Сам маршрутизатор **завжди увімкнений** — головного перемикача немає. Якщо в авто-черзі немає елементів — планувальник просто 30-секундний no-op.

## :material-plus-circle: Як додати в авто-чергу

Чотири способи кинути друк в авто-чергу:

### 1. Print Modal — тогл "Auto"

В Print Modal (з архівів і з бібліотеки) є тогл **Specific / Auto**. Вибираєш **Auto** — модалка показує:

| Поле | Примітки |
|------|----------|
| Target Model | Заповнюється автоматично з `sliced_for_model` 3MF. За замовчуванням "any" — лиши порожнім, щоб будь-який сумісний принтер міг підхопити. |
| Target Location | Опційний тег кімната/стелаж, якщо ти позначив принтери. |
| Force Color Match | Коли увімкнено, перевірка вимагає принтер що має кожен філамент *і потрібний колір*. За замовчуванням вимкнено — збігається лише за типом. |

Submit — і в БД зʼявляється `AutoQueueItem`.

### 2. Режим `auto_queue` віртуального принтера

Слайсер "Send to Printer" → ВП отримує файл → архівується → потрапляє в авто-чергу. Деталі UI див. [Віртуальний принтер → auto_queue](virtual-printer.md#auto_queue).

Це повністю hands-off шлях "наслайсив і забув": слайсер не знає на якому принтері друкуватиметься, і оператор теж не знає, поки маршрутизатор не вирішить.

### 3. Drag-and-drop на панель Auto-Queue

Кидай **скільки завгодно нарізаних файлів** куди завгодно над **панеллю Auto-Queue** на верху сторінки Queue. Кожен завантажується в корінь бібліотеки й далі проходить Print Modal по черзі, з лічильником `2 / 5` — заблокований у режимі **Auto** (без тогла specific/auto, без printer picker, лише constraint-и auto: target model / location / force-color).

**Цільова модель кожного елемента припнута до його власної `sliced_for_model` і змінити її не можна.** По файлу, а не по прогону: два файли, нарізані під дві різні машини, зберігають дві різні цілі в одному дропі. Ставити її явно, а не лишати порожньою, важливо — порожнє означає «розберись із 3MF», що зазвичай дає ту саму відповідь, але на екрані там, де стоїть обмеження, порожньо, і прогін із десяти файлів не сказав би нічого про те, чого кожен із них чекає.

**Файл без записаної моделі відхиляється** поіменно, ще до відкриття діалогу. Припинати нема до чого й перевіряти нема з чим, а поставити його на здогад означало б лишити елемент чекати машини, якої ніхто не обирав.

Форма auto-режиму більше й не пропонує ціль, на якій файл не піде. Вибір невідповідної моделі ніколи не падав помилкою — він давав елемент, що чекає принтера, який його ніколи не візьме, і на екрані нічого цього не пояснювало.

Кнопка **Завантажити з бібліотеки** на панелі відкриває той самий [пікер файлів](print-queue.uk.md#нагрузити-чергу-з-бібліотеки), де запропоновано кожен друкований файл, а не лише під одну машину.

Захищено правом `queue:create`. Панель рендериться завжди, навіть порожня — drop-target постійно доступний; підказка empty-state нагадує про drag-drop при першому відкритті.

### 4. REST API

```http
POST /api/v1/auto-queue/
{
  "library_file_id": 42,
  "target_model": "P1S",
  "force_color_match": false
}
```

Повна схема — у [API reference](../reference/api.md). Quantity > 1 створює N рядків одним викликом (та ж семантика `batch_id`, що й у `print_queue`).

## :material-monitor-dashboard: Панель AutoQueuePanel на Queue dashboard

На сторінці Queue є **панель Auto-Queue** над картками per-printer черг. **Рендериться завжди**, тож drop-target постійно доступний; коли pending-айтемів немає, панель згортається до однорядкової підказки про drag-drop.

З **0.5.5** панель — справжня черга, а не просто купа:

- **Елементи йдуть у справжньому порядку диспетчеризації.** Сусідні копії одного завдання згортаються в компактний рядок **×N**; рядок розгортається в окремі копії.
- **Тягнеться все.** Згорнутий батч рухається як блок, розгорнута копія — будь-куди в порядку: постав п'ять копій A, додай дві B, витягни одну B наперед і залиш другу вкінці — список покаже саме це. З увімкненим **Queue Shortest First** ручки перетягування ховаються, а підказка пояснює, що порядком володіє дистриб'ютор.
- **Кожна копія редагується в повному діалозі Schedule** — тому самому, що й per-printer черга: цільова модель і локація, розклад, опції друку, макроси. Редагування батча застосовується до всіх його копій одразу; окрему копію також можна редагувати, видалити чи примусово призначити саму по собі.
- Кожен рядок, як і раніше, показує мініатюру, назву, плейт, цільову модель, розрахунковий час і причину очікування, коли придатного принтера немає.

Щойно елемент призначається на принтер — він зникає з панелі і зʼявляється в чергу того принтера з невеликим бейджем "auto-assigned".

## :material-filter-variant: Правила придатності

Гелпер `find_eligible_printer` вважає принтер придатним, коли виконується **все** з нижченаведеного:

| Перевірка | Деталі |
|-----------|--------|
| **Не виключений з розподілу** | Іконка-маршрут на картці черги принтера вмикає/вимикає, чи може маршрутизатор взагалі слати туди роботу — виключений принтер має пілюлю «без авто-черги» і пропускається (для машин, зарезервованих під ручні завдання). Це не пауза: пауза зупиняє всю диспетчеризацію тієї черги, а виключення лише каже маршрутизатору везти нову роботу деінде. |
| **Вільний узяти роботу** | Зараз не друкує і ще не тримає поставленого завдання. Чи може принтер **стартувати просто зараз** — підтвердження очищення столу, сушіння, ступінчастий старт — тут свідомо **не** перевіряється; див. [Маршрутизація — це не диспетчеризація](#маршрутизація-це-не-диспетчеризація) нижче. |
| **Збіг моделі** | Якщо вказано `target_model`, код моделі принтера має дорівнювати йому. |
| **Збіг локації** | Якщо вказано `target_location`, тег локації принтера має дорівнювати йому. |
| **Типи філаменту** | Кожен потрібний тип філаменту має бути в якомусь завантаженому слоті (AMS або external spool). |
| **Збіг кольору** | При `force_color_match=true` hex кольору теж має збігатися для кожного філаменту — **як і вид філаменту**, див. нижче. |
| **Filament-overrides** | Будь-яка per-print заміна (наприклад "використати PLA Tough замість PLA") застосовується перед перевіркою завантажених слотів. |

Tie-breaker — коли придатних принтерів кілька:

1. **Найменший ужиток філаменту** (коли увімкнено налаштування `prefer_lowest_filament`, за замовч. вимкнено). Бере принтер у якого AMS-слоти мають найменший залишковий грамаж по потрібним філаментам — лишає "свіжі" котушки на серйозніші завдання.
2. Інакше — принтер з найменшим id.

### Точний збіг кольору відрізняє PLA Matte від PLA Basic

Принтер повідомляє будь-який різновид PLA просто як **`PLA`** — Basic, Matte, Silk і решта розрізняються лише **кодом пресета філаменту**, який слайсер записав у файл.

Тепер точний збіг враховує цей код, і він тримається аж до лотка: принтер із двома білими котушками різних видів отримує саме ту, яку просили, а не ту, що трапилася першою. Раніше завдання, нарізане під **White PLA Matte**, зараховувало машину з **White PLA Basic** як точний збіг і друкувало на ній — фінішне покриття виходило не тим, і ніщо на екрані на це не натякало.

!!! info "Код пресета — це не колір"
    Разом із цим полагоджено й зворотну помилку. Код пресета ідентифікує *вид*
    філаменту, а Bambu продає кожен вид у кожному кольорі — але збіг коду читався
    як доказ, що котушка ще й потрібного кольору. З однією завантаженою котушкою
    Matte кожне завдання, яке хотіло Matte, збігалося з нею **хай якого вона була
    кольору**: діалог друку показував зелену галочку і «Ready» для слота, який
    хотів темно-червоний, проти лотка з темно-зеленим.

    Тепер колір оцінюється на лотку, який реально обрано. Вид філаменту й далі
    вирішує між лотками, що **збігаються** за кольором, — тож завдання під Matte і
    далі віддає перевагу котушці Matte перед Basic, — але більше не б'є колір. Лоток
    потрібного виду в неправильному кольорі використовується, лише коли нічого
    кращого немає, і звітується як **розбіжність кольору**. Полагоджено в усіх трьох
    місцях, де воно жило: діалог друку, мапінг слотів черги й мапінг auto-queue.

Котушки, які **не** повідомляють коду пресета — сторонній філамент і файли, нарізані до того, як принтери почали його записувати, — і далі збігаються за матеріалом і кольором, як завжди; тож ніщо, що працювало раніше, не починає чекати.

## :material-directions-fork: Маршрутизація — це не диспетчеризація

Обрати, якому принтеру належить завдання, і вирішити, коли його можна почати — два різні питання, і відповідають на них у двох різних місцях.

Роутер відповідає лише на перше. Він віддасть завдання принтеру, який **не може** стартувати просто зараз — тому, що чекає підтвердження **«Очистити стіл»**, міняє стіл, сушить або притриманий ступінчастим стартом. Завдання тоді **видимо** лежить у черзі того принтера, доки той не буде готовий, і всі перевірки безпеки спрацьовують тоді, коли це справді має значення.

До **0.5.1.2** роутер узагалі відмовлявся скеровувати роботу на такий принтер. Звучало безпечніше, але безпечніше не було: черга принтера лишалась порожня, тож на екрані ніщо не пояснювало затримку, а плашка **«Очистити стіл»** — яка зʼявляється саме з черги принтера — не мала шансу показатись. Оператор бачив простоюючі машини, названі зайнятими, і ферму, що виглядала мертвою. Саме **розміщення** роботи робить причину видимою.

Принтер, який **готовий**, усе одно виграє, коли є з чого вибирати.

## :material-fire-off: Сушіння має нижчий пріоритет за друк

[Авто-сушіння черги](ams.md#автоматична-сушка-через-чергу) тримає котушки сухими між друками. Коли **Settings → AMS Display Thresholds → Queue Auto-Drying** у типовому **неблокуючому** режимі (`queue_drying_block=false`, *"друк має пріоритет над сушінням"*), завдання, додане **напряму** до принтера, вже зупиняє поточний цикл сушіння й починає друк.

Авто-черга поводиться так само, і з **0.5.1.2** робить це **ранжуванням**, а не виключенням: принтер, вільний узяти роботу, але зайнятий сушінням, завдання отримує — просто програє тому, хто може почати негайно. Per-printer dispatch тоді зупиняє цикл сушіння й починає друк (той самий крок `_stop_drying`, описаний у [AMS → Авто-сушіння черги](ams.md#автоматична-сушка-через-чергу)).

Коли Авто-сушіння черги у **блокуючому** режимі (`queue_drying_block=true`), сушіння й далі тримає чергу — завдання чекає в черзі того принтера, доки цикл сушіння не завершиться, точно як чекало б завдання, додане напряму.

!!! note "Поведінка додана у 0.4.5"
    До 0.4.5 авто-черга вважала принтер, що сушиться, просто "зайнятим" і пропускала його, тож авто-скероване завдання могло чекати за циклом сушіння, хоча додане напряму завдання отримало б пріоритет. Найпомітніше на фермах P2S / H2 з увімкненим авто-сушінням AMS.

## :material-clipboard-text: AMS-мапінг на момент призначення

Коли маршрутизатор копіює авто-чергу в per-printer `print_queue`, він **обчислює AMS-мапінг тут і зараз** з поточного стану котушок принтера — не на момент сабміту. Тож якщо ти переставив котушку між сабмітом і диспатчем — призначений мапінг відображає нову котушку. Початкові `filament_overrides` з auto-рядка застосовуються першими, потім авто-мапінг заповнює решту слотів.

## :material-link-variant-off: Семантика cancel / edit

| Дія | Ефект |
|-----|-------|
| Cancel pending авто-черги | Рядок видалений. Жоден принтер його не бачив. |
| Cancel assigned авто-черги | Скасовується **per-printer елемент**, якого створив маршрутизатор. Auto-рядок лишається у `assigned` для аудиту. |
| Редагувати `pending` елемент | Повний діалог Schedule — цільова модель / локація, розклад, опції друку, макроси. Редагування батча застосовується до кожної копії; окрема копія редагується сама. |
| Редагувати після призначення | Редагуй per-printer елемент черги. |

## :material-lightbulb: Коли користуватися

| Сценарій | Рекомендація |
|----------|--------------|
| Один принтер | Пропусти авто-чергу, користуйся звичною per-printer чергою — без overhead на маршрутизацію, простіший UI. |
| 2-3 принтери однієї моделі | Авто-черга — золотий варіант для load-balancing: кидаєш завдання, планувальник розгрібає на той що звільнився першим. |
| Змішана ферма по моделях | Авто-черга з явним `target_model` per job — той самий load-balancing у межах моделі, без кросу між моделями. |
| Кольоро-чутливі завдання (логотипи, вивіски) | Увімкни `force_color_match` — завдання не диспатчиться на принтер з не тим кольором. |
| Hands-off потік від слайсера | ВП у режимі `auto_queue` + авто-черга → повністю unattended slice → print pipeline. |

## :material-history: Перехід зі звичайної черги

Якщо ти користувався опцією **"будь-який принтер моделі X"** у пікері per-printer черги — це legacy single-tier router. Він досі працює, але авто-черга його перевершує:

| Можливість | Legacy "any of model X" | Авто-черга |
|------------|--------------------------|------------|
| Бере вільний принтер вказаної моделі | так | так |
| Збіг типу філаменту | ні — оператор сам перевіряє | так |
| Збіг кольору | ні | опційно (`force_color_match`) |
| SJF + захист від голодування | ні | так |
| Фільтр локації | ні | так |
| Видима панель "очікування" з причинами | ні | так |
| Інтеграція з ВП | лише proxy | окремий режим `auto_queue` |

Авто-конверсії немає — існуючі per-printer елементи продовжують працювати. Користуйся авто-чергою для нових завдань, де рішення про маршрутизацію можна відкласти.
